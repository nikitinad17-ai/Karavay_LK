# Контрольный заказ в тестовой КИС

Снимок владельца 17.10.2026 17:22 МСК: доступны прежние три тестовых входа,
preferredClient=2. Снимок 17:37: текущий OpenAPI по-прежнему описывает
`CreateOrderRequest {Id_clt,DateOrd,Product:[{Id_prd,KolSht}]}`. Шлюз уже отправляет
эти поля. Перебирать новые названия JSON-полей для записи оснований нет.

`Karavay-Control-Order-20261017.ps1` запускает отдельную операторскую диагностику
на VM через одну SSH-сессию. Это **один реальный контрольный POST в тестовую КИС**
по её документированному контракту. Это не установщик и не изменение браузерной
архитектуры: клиент продолжает использовать `/service/*`.

1. Сервис подтверждает environment=test-kis и единственный allowlisted тестовый
   вход одной точки; проверяются роль owner, покупатель, получатель и разрешение
   создания через публичный gateway. Пароль кабинета не нужен.
2. Считывается текущий OpenAPI с VM. Подбирается одна фактическая позиция из
   датированной матрицы на завтра, с ценой и допустимым количеством. Пустой
   минимум — только лотки, неизвестная укладка отклоняется. Указанный минимум и
   минимальная сумма соблюдаются; отсутствующая минимальная сумма не выдумывается.
3. На VM до POST сохраняется приватное состояние без токена. Выполняется один
   прямой POST `/api/v1/orders`, **без PocketBase Authorization**. Это изолирует
   сам KIS API от реализации отправки шлюзом и даёт полный фактический ответ.
4. Если КИС подтвердила ID, состав и наличие заказа проверяются через
   `/service/orders/{id}` и `/service/orders` под тестовым PB-пользователем.
   Никаких локальных/выдуманных строк истории не добавляется.

Результат успеха: `CONTROL_ORDER_HISTORY_OK: KIS id=...`. При отказе выводятся
`KIS_HTTP`, `KIS_MESSAGE`, `CONTROL_STOP`; полный ответ и запрос остаются в JSON
на VM, путь выводится как `CONTROL_STATE`. В штатных установщиках POST КИС
по-прежнему не выполняется.

Повтор проверяет сохранённый ID либо останавливается без нового POST. Блокировка
защищает и от параллельных запусков. При таймауте/неясном результате повторная
запись запрещена. Флаг `-NewAfterRejection` разрешает новый контроль только после
сохранённого явного HTTP 400/success=false и архивирует прежний отказ; его следует
применять после устранения подтверждённой ошибки. Он не сбрасывает неизвестный
результат и не создаёт новый заказ после успеха.

Успешная прямая запись с чтением через gateway подтвердит только эти границы.
Создание заказа именно через браузер/gateway затем проверяется отдельно. При
прямом отказе `aId_Clt` получаем воспроизводимый документированный запрос и ответ
для исправления обработчика КИС; нельзя выдавать тест фикстуры за успех VM.
