# 3.8.2 — проверенные сценарии с историей КИС

17.10.2026 владелец подтвердил: клиент 2 возвращает count=0/total=0, затем поиск
по 40 получателям покупателей 2/3 не нашёл истории. Это не доказательство пустоты
всей КИС. Выбор этих компаний по первым записям справочника не обеспечил полный
тестовый сценарий. Фиксировать их в новом пакете больше не требуется.

Актуальный установщик `Karavay-Test-3.8.2-Lots-Fix.ps1` из Downloads:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\Downloads\Karavay-Test-3.8.2-Lots-Fix.ps1"
```

Для отдельного исправления лотков/штук в текущем клиенте добавьте `-ClientOnly`.
Этот режим использует `scripts/install.py --apply`, сохраняет текущую тестовую
конфигурацию и не выполняет подбор/создание новых аккаунтов. Правила количества:
`classic-release/QUANTITY-RULES.md`. Описанный ниже полный подбор выполняется
при запуске без этого флага.

На VM сначала выполняются только чтения:

1. Полный справочник покупателей; проверка активности по карточкам. НЕВА,
   ПРОМТЕХСБЫТ и прежние KIS ID 299271/300182 исключены.
2. Подтверждённый на VM `/payers/{id}/orders` **без query-параметров**, затем карточка заказа
   для определения получателя. Проверяется весь полученный справочник (защитный
   предел 10 000 записей); время поиска ограничено 900 секундами.
3. Активность/принадлежность получателя, его собственный `/clients/{id}/orders`,
   доступность первых 20 карточек, хотя бы один заказ с валидным составом.
4. Матрица на завтра (СПб), группа 1 или 0, товары с ценами.

Нужны **два разных покупателя**, прошедших все проверки. Иначе сообщение
`HISTORY_SCENARIOS_NOT_FOUND`, без замены приложения/прав/пользователей. Причины
чтения выводятся отдельно от пустых выдач. Это сигнал проверять данные/контракт
тестовой КИС; повторный перебор тех же 40 точек не предлагается.

После успешного подбора создаются три новые учётные записи:

- `demo.test.point.v382@example.test` — найденный получатель первого покупателя;
- `demo.test.buyer.v382@example.test` — все получатели первого покупателя;
- `demo.test.multi.v382@example.test` — все получатели обоих покупателей.

Названия/коды выводятся в `HISTORY_READY` из фактического ответа КИС. Старые
учётные записи 3.8.1 и их права сохраняются. Новый конфиг показывает три новых
кнопки. Владельцем при наличии подходящего поля/записи назначается «Менеджер
Каравай», права и приложение менеджера не меняются.

У первого/второго сценария сразу выбран получатель с проверенной историей;
у третьего сначала выбирается покупатель. Для первого покупателя также
предлагается проверенная точка. Дата/группа прайс-листа берутся из проверки
матрицы, а не назначаются независимо. Это только начальные значения: права,
смена получателя, корзина и серверная проверка остаются штатными.

После установки каждый тестовый токен повторно читает **историю, состав и
каталог через публичный gateway**, а не только внутренний KIS API.
Успех: `TEST_3.8.2_HISTORY_READY`. F5 обновляет токен/права/настройки.

Обновление сохраняет резервную копию, возвращает файлы при ошибке, не откатывает
бизнес-БД и принятые заказы. Новые аккаунты имеют отдельные ID, поэтому прежние
права/пароли не переписываются. Повтор использует ранее найденные сценарии и
проверяет их заново; отключённые записи не включаются автоматически.

Реальный POST заказа всё ещё не подтверждён: известное расхождение `aId_Clt` не
исправляется выдуманными параметрами. Установщик заказов не создаёт. Проверки на
изолированном PB/Chromium и фикстуре КИС не заменяют результат на VM.

Источники: `select-history.py`, `install-history.py`, `install-test.py`,
`1792260000_test_history_users.js`. Сборка `build-package.py` теперь выпускает 3.8.2.

## Исправленная сборка History-Fix

Этот промежуточный пакет заменён сборкой KIS-Read ниже. История диагностики:

По снимку владельца первая 3.8.2 остановилась: verified buyers=0, empty buyer
histories=0, read/contract errors=100. Это не доказательство отсутствия заказов.
В сохранённом на VM 14.10.2026 OpenAPI `PayerOrdersResponse` имеет поля `Id_pay`
и `Orders`, а `GET /payers/{id_pay}/orders` описывает отдельный query `Id_pay`.
Изначальный подбор ошибочно ожидал массив. Исправлено: явный документированный
query, нормализация контейнера с проверкой ID, nullable Orders как пустой список.
ClientOrdersResponse также поддержан в gateway: `id_clt/Orders`, вместе с ранее
фактически полученным плоским массивом. Чужой ID/некорректный тип отклоняются.
Три одинаковые ошибки верхнего чтения останавливают поиск, а не повторяются 100 раз.
Фактическая первая ошибка на снимке не видна; точная причина всех 100 отказов
без её текста не установлена. Исправление основано на первичном OpenAPI, не на
подборе недокументированных полей. Формат POST заказа не изменён.

## KIS-Read — подтверждение фактического запроса, 17.10.2026

Снимок (4): КИС HTTP 400, код -20001 — атрибуты `id_pay`, `offset`, `limit`
не принадлежат сущности `order`. Эти query-параметры исключены. Снимок (6):
тот же `/payers/428125/orders` без query вернул HTTP 200,
`{"success":true,"data":[]}`. Это подтверждает рабочий маршрут и пустую историю
именно этого покупателя, не всей КИС. Архивный OpenAPI здесь расходится с
фактической проверкой параметров сервера.

Подбор обрабатывает плоские массивы и контейнеры с проверкой владельца.
При HTTP-ошибке скрипт теперь выводит `error.message` КИС (ограниченный размер,
одна строка), без Oracle stack/details, токенов и совета повторять неисправный
запрос. Три одинаковые ошибки по-прежнему останавливают поиск. Успешный выбор
двух покупателей на VM и реальный POST пока не подтверждены.

## Продолжение поиска после первых 100 покупателей

Снимок (7): 100 пустых историй, 0 ошибок чтения, 0 выбранных покупателей.
Это прежний лимит поиска, не проверка всего справочника. Снимок (8): контрольные
`/payers/300182/orders` и `/clients/300183/orders` также пусты, а прежний архивный
`/orders/48393204` возвращает HTTP 400 «Не найден order». Нельзя объявлять сброс
БД или пустую историю всей КИС по этим результатам.

Лимит расширен на весь допустимый справочник с общим бюджетом 15 минут.
По-прежнему требуются два покупателя с собственными проверенными получателями,
историей, составом заказа и матрицей; при неуспехе приложение не изменяется.
Для уже распакованных на VM файлов достаточно обновить два значения лимита,
затем запустить прежний `install-history.py --apply`. Повторное скачивание
пакета не обязательно. Подготовленный пакет KIS-Read также обновлён.
