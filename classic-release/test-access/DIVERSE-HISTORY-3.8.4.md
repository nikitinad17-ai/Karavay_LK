# Разные покупатели с историей — 27.10.2026

Снимок владельца подтвердил установленные v383-входы: первые два используют
Назарову, третий — Назарову/Кузьмину. Это были разные области доступа с одним
покупателем по умолчанию. История не участвовала в их выборе после исправления
ошибки прайса. Непустая история реальной КИС для них не подтверждена.

Новый отдельный пакет `Karavay-Different-Buyers-History-20261027.ps1` подбирает
**трёх других покупателей**. Текущие покупатели v383, известные производители
Каравай/Паляница и ранее отклонённые организации исключены. Классификация
остальных карточек опирается на доступный справочник КИС: универсального признака
«производитель/покупатель» API не предоставляет.

## Сценарии

| Email | Область | Старт |
| --- | --- | --- |
| demo.test.point.v384@example.test | Одна точка покупателя A | A и его точка с историей |
| demo.test.buyer.v384@example.test | Все активные точки покупателя B | B и его точка с историей |
| demo.test.multi.v384@example.test | Все активные точки покупателей C и B | C и его точка с историей |

Названия A/B/C и ID заранее не выдумываются: их выводит `DEMO_PLAN` после чтения
КИС. Фиктивны только email аккаунтов, не контактные email организаций.

## Как подтверждается история

Проверяются активная карточка покупателя, список его получателей, принадлежность
и активность карточки получателя, **его** `/clients/{id}/orders`, все заголовки
первой страницы и непустой корректный состав хотя бы одного заказа на ней.
Пустой `/payers/{id}/orders` не используется как повод пропустить получателей.
История читается без неподдерживаемых query-параметров и без фильтра даты.
Прайс на завтра читается отдельно (Group 1→0); HTTP 400 прайса не исключает
покупателя с подтверждённой историей. Цены и заказы не подменяются.

Поиск сохраняет только IDs и прогресс в закрытом checkpoint на VM. При повторе
продолжает чтение, заново проверяя найденные истории. Пустые получатели кешируются
на 24 часа; `-Rescan` сбрасывает этот кеш. Ограничение одного запуска — 20 минут
по умолчанию (`-SearchMinutes 1..60`). Если трёх покупателей нет или контракт
повторно ошибочен, действующие входы и приложение сохраняются. После установленной
v384 повтор проверяет тот же набор, автоматически покупателей не меняет.

## Изменения и установка

Клиент сохраняет дизайн/шесть разделов/лотки/корзину/заказ. Изменены версия и
начальный выбор разрешённого preferredPayer тестовой сессии; ручной выбор при
последующем обновлении контекста сохраняется. Обычный вход с несколькими покупателями
по-прежнему требует выбора. Новый helper поддерживает прежний config v1 и v2
с тремя разными стартовыми покупателями.

Preflight проверяет TEST KIS, PB 0.40.3, схему, hashes HTML/helper/routes и
отсутствие чужих pending migrations. После подтверждения историй добавляются
новые аккаунты v384/их права и три mapping получателей. Старые users/passwords/
rights и файлы менеджера не меняются. При смене файлов создаётся приватная копия;
ошибка проверки или Ctrl-C возвращает прежние файлы. Текущая бизнес-БД не
откатывается поверх новых заказов; созданные миграцией записи могут остаться
в БД после файлового отката, но прежний список демо восстанавливается.

После запуска проверяются три passwordless входа, разные defaults, точные области,
получатели, непустая история/состав через **существующий** `/service/*` и запрет
чужого покупателя. Только после этого выводится `DIVERSE_HISTORY_READY`.
Транспорт блокирует любые записи КИС и любые PB POST, кроме демо-входа;
PB-токен не передаётся КИС, redirects запрещены. Создание заказа/Oracle остаётся
на паузе. Почтовая отправка не выполняется.

Запуск из Windows Downloads:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\Downloads\Karavay-Different-Buyers-History-20261027.ps1"
```

После `DIVERSE_HISTORY_READY` обновить страницу. Прежняя тестовая сессия сбросится
проверкой списка доступных accounts; новые три кнопки покажут реальные названия.
`THREE_HISTORIES_NOT_FOUND` означает, что нужные истории не найдены, а не успешную
установку. Результат настоящей VM/КИС в этой среде ещё не получен.

## Локальная проверка

Автоматизированы реальный urllib/HTTP reader с фикстурой и отсутствие KIS writes,
выбор по recipient history при пустом payer index, ownership и состав, продолжение
поиска/отсутствие истории, SQLite-план/коллизии/повтор/отключённые записи,
файловый откат с сохранением текущей БД. Настоящий JS helper проверяется с ORM-
фикстурой, реальные обработчики list/detail — с подменённым транспортом КИС.
DOM-проверка React покрывает другой preferredPayer, историю, restore и ручной выбор.
Ограничение: бинарник PocketBase/Chromium и PowerShell в текущей среде недоступны;
нет нового запуска на настоящем PB или визуального браузерного прогона. Точный
результат команд проверки фиксируется в PROJECT_CONTEXT после их завершения.
