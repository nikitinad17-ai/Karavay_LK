## Что изменено

- Фирменные стили сохранённого 3.6.4: сине-жёлтая палитра, логотип, навигация, строки продукции с лотками/штуками, корзина и окно проверки. Это перенос оформления на новые данные; визуальное совпадение каждого экрана пиксель в пиксель не заявляется.
- Реальный email-вход через users, обновление сессии, смена временного пароля; покупатели и получатели по новым правам PB, матрица и история из КИС.
- DateOrd — полночь выбранной даты в Санкт-Петербурге (UTC+3). Group=0 — ЗПФ, 1 — ХБИ/прочая продукция. Цена берётся для выбранной даты.
- Размер лотка — kolukl/kol_sht. Минимальное количество — kolshtordmin. Размер упаковки не считается признаком обязательного полного лотка: такой признак в полученных данных отсутствует.
- Проверка заказа показывает реальные цены и количества. Перед POST сервер повторно читает матрицу, проверяет доступность позиции, минимум и совпадение цены. При изменении цены пользователь обновляет прайс-лист; корзина сохраняется для оставшихся доступных товаров.
- Минимальная сумма получателя и признак НДС показываются из КИС. Неизвестная налоговая формула не выдумывается; ограничения суммы и дней доставки остаются на стороне КИС. На клиенте не реализована неподтверждённая трактовка restrictions_day_of_week.
- История загружается страницами по 20, с кнопкой «Показать ещё» и поиском по номеру/дате среди загруженных заказов. Каждый заказ дополнительно проверяется по client_id. Карточка показывает реальные позиции products, цены, количество, суммы и возвраты.
- Шесть разделов сохранены. «Документы» пока сообщает об отсутствии подключения. Редактирование/удаление заказов в этот выпуск не входит.
- Два пользователя (демо), описание ниже. В окне проверки явно указано: их заказы создаются в рабочей КИС.

## Реальный контракт и оставшееся противоречие КИС

Архив Karavay-Order-Contract-20261014.zip получен с VM. В нём успешные GET и OpenAPI. Реальная карточка заказа 48393204 содержит client_id и products с полями id/product_kod/product_name/cena_otp/kol_sht/kol_vzv/sum_all. Формат GET в OpenAPI отличается от живого ответа, поэтому чтение реализовано по фактическому JSON.

POST реализован строго по опубликованному CreateOrderRequest:

```json
{"Id_clt":300183,"DateOrd":1791925200,"Product":[{"Id_prd":425162,"KolSht":15}]}
```

Это пример структуры, НЕ команда создания и НЕ рекомендуемая дата/корзина. Group и проверяемая цена не передаются в КИС: их нет в CreateOrderRequest. Они нужны серверу LK для выбора матрицы и проверки.

**Ранее этот формат возвращал HTTP 400 «Не задан aId_Clt». Полученный OpenAPI его повторяет и не доказывает исправление сервера.** В коде нет перебора названий параметров или повторных POST. Если ошибка сохранится, интерфейс покажет KIS_CONTRACT_MISMATCH. Тогда разработчику КИС нужно исправить соответствие POST /api/v1/orders опубликованной схеме; успешной запись считать нельзя.

Успех показывается только после успешного POST, получения ID и повторного GET: должны совпасть получатель, дата, товарные позиции и количества. Производственный POST остаётся непроверенным до отправки пользователем настоящего заказа.

## Защита от повторов

Добавляется одна закрытая коллекция lk_order_requests. Существующие users/roles/rights/payers/clients не мигрируются. Все API rules журнала — null; пользователь не читает/редактирует его напрямую.

Ключ и отпечаток запроса сохраняются в транзакции до POST. Повтор того же ключа возвращает сохранённый результат; смена содержимого отклоняется. Одинаковая успешная корзина с другим ключом в течение двух минут получает прежний результат. При тайм-ауте/неизвестном результате запрос остаётся заблокирован, в том числе после перезапуска PB. Автоматических повторных записей нет.

В браузере незавершённая отправка хранится в sessionStorage отдельно по ID пользователя, переживает F5 и повторный вход в той же вкладке. «Проверить результат» делает GET. Если запрос ещё не найден, повтор использует ТОТ ЖЕ ключ. Закрытие вкладки может удалить локальную запись, но серверный журнал сохраняется. Не удалять неопределённые записи журнала ради разблокировки: сначала сопоставить их с историей КИС.

## Установка одним блоком из Windows PowerShell

Скачать Karavay-Classic-3.8.0-20261014.zip в обычную папку Downloads текущего пользователя Windows:

```powershell
$package = Join-Path $env:USERPROFILE 'Downloads\Karavay-Classic-3.8.0-20261014.zip'
scp "$package" lindevadmin@192.168.25.98:/home/lindevadmin/
if ($LASTEXITCODE -eq 0) {
    ssh -t lindevadmin@192.168.25.98 "python3 -m zipfile -e /home/lindevadmin/Karavay-Classic-3.8.0-20261014.zip /home/lindevadmin/karavay-classic-380 && sudo python3 /home/lindevadmin/karavay-classic-380/scripts/install.py --apply"
}
```

Установщик проверяет PB 0.40.3, известные контрольные суммы клиента 3.7.2/3.7.3 и gateway, необходимые поля и чужие неприменённые миграции. При расхождении останавливается до изменений. Во время короткой остановки PB сохраняет резервную копию, заменяет клиент и обработчик истории, добавляет checkout-модуль/маршруты и закрытый журнал. Менеджер, его файлы и миграции не заменяются. После запуска проверяет HTML и 401 JSON новых маршрутов. Ни установка, ни seeder не создают заказ в КИС.

Успешная строка: CLASSIC_3.8.0_INSTALLED. Адрес: http://192.168.25.98:8090/ — обновить Ctrl+F5.

Резервная копия: /opt/.karavay-classic-before-*. Команду отката установщик печатает с точным путём. Откат возвращает только файлы приложения; текущие пользователи/права/журнал сохраняются, чтобы не потерять новые записи и защиту от дублей. Резервная копия БД существует для ручного восстановления, автоматически поверх текущих бизнес-данных не накатывается.

Скрипт спрашивает email/пароль администратора PB и временный пароль демо-пользователей локально в терминале; пароль не выводится и не сохраняется в файле. При первом входе обязательна смена пароля. Администраторские данные в чат не присылать.

Скрипт сверяет свежие GET КИС. При отсутствии покупателя в PB регистрирует его настоящий ID/код/название. Если установленная схема требует реальный контактный email покупателя, создание останавливается, контакт не выдумывается. Существующие покупатели и чужие учётные записи не изменяются. Новые пользователи включаются только после записи и сверки всех прав. Повторный запуск не меняет выбранных покупателей и не сбрасывает пароли. При частичном сбое создаваемый пользователь остаётся отключённым; повтор завершает только собственный сохранённый план. План содержит IDs без секретов в ~/.karavay-other-demos-20261015.json (0600). Успешно созданный и затем отключённый пользователем аккаунт скрипт не включает. Старые demo.buyer/demo.outlet не удаляются и не переназначаются.
