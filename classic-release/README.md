# КАРАВАЙ 3.8 — подготовка старого интерфейса для нового PocketBase

Дата: 14.10.2026. Статус: подготовительная версия, НЕ готовый выпуск создания заказов.

## Что готово

- Взяты фирменные CSS из сохранённого 3.6.4 Demo Showcase, сохранены логотип, сине-жёлтая палитра, навигация и оформление строк продукции с лотками/штуками.
- Новый React entrypoint `src/classic/main.tsx`; старый frontend и менеджер не заменяются.
- Реальный вход `users` по email, refresh, выход, смена временного пароля через уже существующий `/service/account/change-password`.
- Покупатели `/service/context`, все страницы разрешённых получателей `/service/clients`, каталог `/service/catalog`, история `/service/orders`.
- DateOrd — полночь Europe/Moscow; Group=0 — ЗПФ, 1 — ХБИ/прочая продукция.
- Корзина, перевод размера лотка `kol_sht` в штуки, минимум SKU `kolshtordmin`, цены `cenaotp`, экран проверки заказа, мобильная панель.
- Переключение покупателя/получателя/даты требует подтверждения потери корзины. Устаревшие ответы не меняют новый контекст.
- Состав и запись не подменяются демонстрационными данными. Во всех реальных запросах отсутствуют внешние `/api/v1`.
- Подготовлены отдельно два дополнительных read-only backend-маршрута с проверкой роли, прав и принадлежности заказа; установщик preview их не устанавливает.

## Что блокирует завершение

Реальный POST КИС ранее возвращал HTTP 400, `Не задан aId_Clt` при отправке `Id_clt/DateOrd/Product`. Ни успешного ответа, ни подтверждённого формата строк заказа пока нет. Исторический mock-контракт не является контрактом рабочей КИС.

Нужен архив `Karavay-Order-Contract-20261014.zip`, создаваемый прилагаемым read-only сборщиком. По нему предстоит подключить точные поля создания и состава, серверную проверку количеств/цен и защиту от дублей, проверить результат записи на согласованном сценарии.

В этой версии `create=false` и `itemsAvailable=false`; POST не подключён. Кнопка отправки недоступна. GET карточки возвращает только подтверждённые поля шапки; состав не выдумывается. Детальный backend пока только подготовлен и проверен на отдельном PB.

Обязательность полного лотка не выводится из одного размера упаковки. Поле lotOnly в подтверждённой matrix не получено. Минимальная сумма и признак НДС доступны в отдельных карточках КИС, но правила расчёта с итогом ещё не подтверждены; это не выдуманный нулевой минимум. Словарь статусов тоже не придуман: показано значение КИС.

| Email | Имя | Область прав |
|---|---|---|
| demo.buyer@karavay.example | Покупатель двух организаций (демо) | Покупатели КИС 300182 и 299271, все их активные получатели |
| demo.outlet@karavay.example | Получатель одной точки (демо) | Только получатель 300183 покупателя 300182 |

Оба имеют бизнес-роль owner (без прав менеджера), чтобы проверять различия области доступа, а после подключения записи — оформление. Email вымышленные в зарезервированном домене `.example`. Отправка почты на них не выполняется. Названия/коды/связи получателей скрипт проверяет свежими GET КИС. Существующие покупатели должны быть зарегистрированы и активны в PB; они не переименовываются и не перезаписываются.

Пользователи на VM ещё НЕ созданы. Для создания требуется запустить на VM:

```bash
python3 /home/lindevadmin/karavay-classic-38/scripts/Seed-Demo-Users.py --apply
```

Терминал спросит администратора PB и временный пароль для демо-пользователей, без вывода паролей. При первом входе нужна смена пароля. Секреты не отправлять в чат. Повторный запуск сверяет записи, не сбрасывает пароли и не создаёт дубли. При частичном сбое новый пользователь остаётся отключённым; существующие учётные записи не изменяются. Без `--apply` — только план чтения.

Демо — пометка учётной записи, а не копия КИС: источники покупателей и заказов реальные. Скрипт пользователей не создаёт никаких заказов.
