# Контекст проекта

## Актуальная контрольная точка — 2026-10-08

Решения владельца из последнего чата перенесены в GitHub. Этот блок описывает
актуальный рабочий контур и дальнейшую архитектуру; расположенная ниже реализация
React 3.5 остаётся состоянием исходников `main`, а не схемой действующей VM.

| Слой | Состояние |
| --- | --- |
| React в `main` | 3.5, `buyers/outlets`, вход по `kis_code`; бизнес-данные КИС отключены |
| React в `feature/v3.6-user-multi-buyer-auth` | 3.6, ранняя модель `users/user_buyers/buyers/outlets` |
| Сохранённый рабочий standalone 3.6.3 | В ветке `feature/v3.6.4-demo-showcase`, модель `users/roles/rights/payers/clients`, вход по email |
| PocketBase VM | `192.168.25.98:8090`; вход и права подтверждались владельцем, независимой проверки VM в этой передаче нет |
| Demo Showcase 3.6.4 | Реальный PB для авторизации/прав, локальные демо-товары и заказы; не интеграция КИС |
| КИС | Внутренний Web API `http://serv15db:55580/api/v1`; успешное реальное чтение ещё не подтверждено |
| Публичный бизнес-API | Согласован `/service/*`; серверные handlers предстоит реализовать |

### Последние принятые решения

- PocketBase остаётся на внутренней VM и сам выполняет роль шлюза через `pb_hooks`.
- Браузер использует HTTPS и PB-токен; бизнес-маршруты — `/service/context`,
  `/service/catalog`, `/service/orders`. Внешнего `/api/v1` в новой схеме нет.
- PocketBase проверяет активные user/role/rights/payer/client и обращается к
  внутреннему `/api/v1` КИС. Ответ проверяется и фильтруется на сервере.
- Отдельный секретный ключ / сервисный токен КИС не используем. Прежнее
  предположение о его обязательности отменено; доступ без ключа надо проверить с VM.
- Общее право с пустым client даёт всех активных получателей этого payer;
  иначе разрешено объединение конкретных clients. Плательщиков/получателей
  напрямую для входа не используем.
- Email пользователя обязателен; восстановление через email требует отдельной
  проверки почтовой настройки. Один payer выбирается автоматически, несколько
  требуют выбора; F5 обновляет auth и права, logout/смена payer очищают контекст.
- Сначала готовим `GET /service/catalog` и приёмку 401 без входа, 403 без права,
  200 с реальным разрешённым каталогом. Создание/изменение заказов — после чтения.
- Для внешнего доступа добавляется HTTPS reverse proxy и защищённое соединение
  до VM. Российский VPS + WireGuard — один из вариантов; публичный домен
  `lk.karavay.spb.ru`, DNS/сертификат и туннель ещё не подтверждены.

Подробности и критерии: [модель доступа](docs/POCKETBASE_ACCESS_MODEL.md),
[схема PocketBase → КИС](docs/POCKETBASE_KIS_GATEWAY.md),
[передача контекста и проверенные ветки](docs-project/CHAT_HANDOFF_2026-10-08.md).

Старые документы `buyers/outlets`, миграции `user_buyers` и контракт с внешним
`/api/v1` сохраняются как история предыдущих этапов. Они не заменяют актуальную
схему и не должны применяться поверх работающей VM без сверки. Перенос новых
решений в React требует отдельной согласованной реализации, а не замены env-имён.

## Цель

Личный кабинет покупателей АО «КАРАВАЙ» для оформления и сопровождения заказов. Один покупатель может управлять множеством получателей/торговых точек; целевой масштаб — около 600 точек.

## Реализация main: версия 3.5 TypeScript + PocketBase directory

React + TypeScript является основной реализацией. Vanilla 3.2 остаётся исторической опорой, React 3.3 — функциональной базой миграции.

### Готово

- React 18/Vite 8 и полный набор экранов 3.2;
- каталог из 111 демонстрационных товаров и 7 категорий;
- роли покупателя и получателя;
- создание, просмотр, повтор, корректировка и отмена заказа;
- окно проверки заказа и мобильная закреплённая панель;
- единые ограничения минимального количества и кратности лотка;
- блокировка повторной отправки;
- подтверждение сброса несохранённых правок;
- immutable-обновления заказов;
- request gate для зависящих от состояния загрузок;
- recovery UI при ошибке начальной загрузки;
- unit, jsdom integration и Playwright E2E;
- production base `/react-test/`.
- строгая типизация всего `src/`, mock API, unit/integration и Playwright-сценариев;
- единый файл доменных контрактов `src/types.ts`;
- `npm run check` начинается с `tsc --noEmit`;
- `must_change_password=true` блокирует вход отдельной безопасной ошибкой.
- directory-режим загружает buyer/outlets из PocketBase без фиксированных demo-кодов;
- покупатель получает только связанные активные точки, получатель — только себя и родительского покупателя;
- матрица, заказы и документы в directory-режиме отключены до серверного API КИС;
- готов один HTML для `pb_public` и отдельная инструкция настройки правил.

## Архитектурные решения

- Состояние: Context + reducer, без внешнего state manager.
- Навигация: внутренний route state; URL-маршрутизация пока не нужна.
- Бизнес-правила количества: `src/orderRules.ts`.
- Сетевой слой: типизированный `api<T>()` и демонстрационный fetch-adapter в `src/mockApi.ts`.
- Конкурентные загрузки: поколения запросов в `src/requestGate.ts`; применяется к покупателю, матрице и последнему заказу.
- Доменные модели и ответы КИС: `src/types.ts`; TypeScript работает в режиме `strict`.
- Сборка: Vite 8, статический base `/react-test/`.

## Дорожная карта версии 3.5 (историческая)

При продолжении нового контура сначала использовать контрольную точку 2026-10-08
и связанные документы выше. Следующий список сохранён для понимания этапа 3.5.

### Этап 2 — реальный контур доступа и КИС

Срез 2.2 реализован локально и готов к проверке на VM:

- зафиксированы `contracts/openapi.yaml`, `contracts/error.schema.json` и таблица auth-ошибок;
- mock API загружается только при явном `VITE_DATA_MODE=mock`;
- production defaults: `pocketbase + remote`, без demo-бандла;
- реализованы вход через auth-коллекции `buyers`/`outlets`, refresh, восстановление и выход;
- токен хранится в `sessionStorage`, пароль и полная auth-запись не сохраняются;
- auth-запросы имеют таймаут и `X-Request-ID`;
- добавлены unit-тесты auth-адаптера и отдельная сборка для `pb_public`.
- добавлена прямая загрузка профиля и relation `buyer → outlets` из PocketBase;
- список точек загружается страницами по 200 записей;
- некорректная схема и отказ API rules блокируют вход, а не превращаются в пустые данные.

Осталось:

1. Создать безопасные тестовые auth-записи `TEST-B-01` и `TEST-O-01` и проверить оба входа на PocketBase.
2. Согласовать фактический URL, авторизацию и ответы API-шлюза КИС.
3. Подключить реальные buyer/outlets, matrix, orders и documents поэтапно.
4. Распространить AbortController, таймауты, correlation ID и централизованное логирование на бизнес-API.
5. Добавить контрактные тесты шлюза и провести пилот на ограниченной группе покупателей.
