## Главное изменение

Демо-бэкенд `api.js` больше не выдумывает собственный контракт — он реализует
все восемь методов из ТЗ с точными именами полей, Unix-таймстемпами и кодами
ошибок. Идентификаторы совпадают с примерами спецификации:
`Id_pay: 288337`, `id_clt: 299756`.

## Методы API (все реализованы и покрыты тестами)

| № | Метод | Путь |
|---|---|---|
| 1 | GET | `/api/v1/payers/{id_pay}` |
| 2 | GET | `/api/v1/clients/{id_pay}` |
| 3 | GET | `/api/v1/matrix/{id_clt}?DateOrd=&Group=` |
| 4 | GET | `/api/v1/orders/{id_pay}?Id_clt=&Id_ord=&last=&offset=&limit=` |
| 5 | GET | `/api/v1/order-details/{id_ord}` |
| 6 | POST | `/api/v1/orders/` |
| 7 | PATCH | `/api/v1/orders/{id_ord}` |
| 8 | PATCH | `/api/v1/orders/{id_ord}/state` |

Аутентификация (`/api/login`, `/api/lookup`) и документы остаются вне ТЗ —
в спецификации их нет.

## Что вернулось из-за ТЗ

**Дата поставки.** `DateOrd` обязателен и в матрице, и в создании заказа —
без даты каталог не запросить. Выбор даты вернулся в форму.

**Дни недели.** `ClientDayOfWeek` из `/clients` ограничивает список доступных
дат. Слоты времени при этом не вернулись — их в ТЗ нет.

## Что появилось

**Группы ЗПФ / ХБИ.** Матрица и заказ параметризованы группой. ЗПФ и ХБИ
нельзя смешать в одном заказе — бэкенд отдаёт 400.

**Матрица по получателям.** Ассортимент и цены индивидуальны для каждой точки.
При смене получателя каталог перезагружается, отсутствующие позиции вычищаются
из корзины с уведомлением.

**Скидка отделена от акции.** `ProcSkd` действует на весь ассортимент — это
условие договора, а не акция. Акцией считается позиция, где скидка выше
базовой клиентской. Признака акции в ТЗ нет, он выводится расчётом.

**Возвраты.** `KolVzv` показывается отдельным столбцом в карточке заказа,
если по заказу есть возвраты.

## Изменённые правила

| Было (v1.9) | Стало (v2.0, по ТЗ) |
|---|---|
| Правка до 17:00 дня перед доставкой | Правка пока `State = «Принят»`; дальше 422 |
| Отмена меняла статус локально | `PATCH /orders/{id}/state` `{State:"delete"}` |
| Блокировка → заказ в статусе `hold` | 422 «Заказ превышает сумму доверия или баланс» — заказ не создаётся |
| Статусы: accepted/picked/shipped/delivered | Принят · Маршрутизирован · В пути · Отгружен · Удален |
| История за 3 месяца | 14 дней плюс все незавершённые |

> ⚠️ Статуса «ожидает разблокировки» больше нет. Раньше заблокированный заказ
> принимался и ждал; теперь КИС его отклоняет. Решение требует подтверждения —
> для клиента разница ощутимая.

## Архитектура

Между КИС и интерфейсом стоит слой адаптеров: `adaptPayer`, `adaptClient`,
`adaptProduct`, `adaptOrder`, `adaptItem`. Интерфейс работает со своими именами
полей, поэтому изменение схемы КИС затрагивает только эти пять функций.

Поля, которых в ТЗ нет (телефоны, ИНН, договор, отсрочка, приёмщик, площадка,
диспетчерская), помечены префиксом `lk_` — видно, что они приходят из
справочника ЛК, а не из КИС.

## Чего КИС не отдаёт

Телефоны (точки, менеджера, ТП), email, ИНН, номер и дата договора, отсрочка
платежа, приёмщик, площадка отгрузки, упаковка продукции, ставка НДС, цена без
НДС, документы. Сумма доверия упоминается в тексте ошибки 422, но самого лимита
в `/payers` нет — клиент не видит, сколько ему осталось.

## Замечания к спецификации

1. **JSON в примерах невалиден:** `"OrdLimitMinSum": 1 000.00` — пробел внутри числа.
2. **Пробелы в именах ключей:** `"KodPay "`, `"id_prd "`, `"CenaOTP "`, `"KolUkl "`.
3. **Нейминг плавает:** `NameProd` / `Name_prod`, `kod_prod` / `kodProd`, `Id_pay` / `id_clt`.
4. **Не указано**, где передаются `DateOrd` и `Group` в `/matrix` — query или тело.
5. **Аутентификация не описана** вовсе, хотя 403 «Нет прав» предусмотрен.
6. **Смешение языков** в поле `State`: значения по-русски, а команда удаления — `delete`.
7. **Номер маршрута и ФИО водителя** показывать не нужно: водитель — персональные данные, маршрут — внутренняя логистика. Полезнее плановое время прибытия для статуса «В пути».
