## Где работать

- `manager-live/pb_public/manager/` — интерфейс.
- `manager-live/pb_hooks/karavay-manager.js` — действия и область доступа.
- `manager-live/pb_migrations/` — добавочные изменения схемы.
- `manager-live/scripts/` — упаковка и установка.
- `manager-live/MANIFEST.json` — проверка файлов и разрешённых предшественников.
- `manager-live/tests/` — интеграция, сессии, установщик, браузерные проверки.

## Текущий интерфейс и данные

Один раздел «Пользователи»: таблица, фильтр ролей, создание, Инфо, Изменить,
Удалить и вход в доступные демо. Форма создания содержит четыре поля: логин,
email, Client/Payer, пароль. После создания она закрывается; назначения
покупателей и получателей открываются вручную внутри «Изменить».

`users.account_type` хранит Client/Payer даже до появления назначений.
Это метка типа, не выдача доступа. Сохранять auth-роли `owner/manager/viewer`,
режим просмотра, обязательную смену временного пароля и существующие пароли.
Client получает конкретные точки, Payer — разрешённых получателей покупателя.
Новый пользователь без `rights` остаётся без бизнес-доступа.

Область менеджера проверяется на сервере. Чужие пользователи/покупатели/точки
недоступны для изменения. Последовательность проверки и транзакции важнее
клиентских фильтров. Обычный установщик 0.9.1 не создаёт заново демо и не меняет
их пароли; `-ResumeSetup` — отдельная явно выбранная настройка старого набора.

## Исправления из проверки

1. При удалении последних назначений через `edit_user` сохраняется
   `manager_owner` текущего менеджера. Старые пользователи больше не исчезают
   из его списка; их можно назначить снова. Проверены пустой и чужой прежний owner.
2. При смене Client/Payer после раскрытия назначений пересоздаются допустимые
   варианты scope. Форма не остаётся с отключённым `client`/`all` и сохраняется.
   Отсутствие права на «всех получателей» не обходится; невалидный scope блокируется.

В ветке исправлений добавлены регрессии и обновлены хеши манифеста. Это ещё
не отдельный выпущенный установщик: перед выпуском выбрать номер патча и
собрать пакет с однозначной версией.

## Как проверить

```bash
npm run check
PB_BINARY=/path/to/pocketbase python3 manager-live/tests/integration.py
node manager-live/tests/session.cjs
python3 manager-live/tests/installer.py
PWSH=/path/to/pwsh python3 manager-live/tests/powershell.py
MANAGER_CHROME=/path/to/chrome-headless-shell CLIENT_HTML=/path/to/client-3.8.5.html PB_BINARY=/path/to/pocketbase python3 manager-live/tests/recipients.py
```

Фактически прошли: 22 общих теста/TypeScript/сборка, 88 HTTP-проверок локального
PB 0.40.3, UI-регрессии через jsdom/HTTP, 16 проверок сессии, 9 установщика,
14 PowerShell 7/Linux. Chromium с клиентом 3.8.5 проверил форму, F5, назначения,
шесть существующих демо, изоляцию, выход, мобильный экран и сессию менеджера.
SSH/SCP и КИС — фикстуры; Windows PowerShell 5.1 и VM нативно не проверены.

Корневой E2E-набор не прошёл на ожидании старой демо-кнопки React 3.5.
Он не проверяет актуальный `/manager/`; для CI нужно запускать специальные
сценарии менеджера и привести общий набор в соответствие выбранной сборке.

## Что делать дальше

Сначала принять и выпустить исправления, затем добавить отдельную CI-проверку
менеджера и общий тест с актуальным клиентом. После этого полезен журнал
изменений пользователей/прав: автор, время, прежнее и новое назначение.
Для рабочего внешнего запуска отключать тестовый вход серверной настройкой.
Клиентский HTML, gateway и бизнес-данные сохранять штатным установщиком;
не заменять их старым комплектом из менеджерской ветки.
