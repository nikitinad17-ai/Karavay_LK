## Карта проекта

Клиент использует React/TypeScript/Vite. Актуальный интерфейс находится в
`src/classic/`, сборка задаётся `vite.classic.config.ts`; упаковка —
`scripts/build-classic.mjs` и `classic-release/`. Клиент содержит обзор,
оформление заказа, историю, точки, документы и профиль. Раздел документов
пока не подключён к реальному источнику.

Менеджер — отдельное приложение HTML/CSS/JavaScript в
`manager-live/pb_public/manager/`, серверная логика —
`manager-live/pb_hooks/`. В 0.9.1 основной экран — таблица пользователей;
создание содержит логин, email, Client/Payer и пароль. Назначения находятся
внутри редактирования. Автоматического мастера после создания нет.

Общий сервер — PocketBase с JavaScript hooks. Доступ определяется активными
`users / roles / rights / payers / clients`. Покупатель объединяет получателей;
`scope=all` даёт доступ к получателям покупателя, `scope=client` — к конкретной
точке. `users.account_type` хранит метку Client/Payer и само по себе прав не выдаёт.
Технические auth-роли `owner / manager / viewer` — отдельная сущность.
Браузер работает через `/service/*`; внутренний API КИС вызывается сервером.

## Две исправленные ошибки менеджера

### Пользователь исчезал после удаления всех назначений

В исходном 0.9.1: открыть существующего пользователя с назначениями, у которого
пустой `manager_owner` либо указан прежний менеджер; удалить все назначения
через «Изменить» и сохранить. Запись оставалась в БД, но исчезала из списка
редактирующего менеджера. Назначить права обратно из интерфейса было нельзя.

Причина: `edit_user` не сохранял владельца пустой записи, хотя отдельное действие
`set_rights` уже делало это. Исправление присваивает текущего менеджера при
явном сохранении пустого набора прав, в той же транзакции и после проверок доступа.
Проверены оба случая прежнего владельца и последующее повторное назначение прав.

### Смена Client/Payer оставляла несовместимый тип назначения

В исходном 0.9.1: открыть пользователя, раскрыть назначения, затем переключить
Client → Payer. В select оставался единственный отключённый вариант `client`;
сохранение отклонялось с `ACCOUNT_TYPE_SCOPE`. Обратное переключение также
не создавало нужный вариант.

Исправление пересоздаёт допустимые варианты назначения с учётом нового типа
и области самого менеджера. Выбранные покупатели и отмеченные точки в текущей
форме сохраняются. Если менеджер не может выдать доступ ко всем получателям,
форма не отправляет пустой или недопустимый scope. Проверены сохранение Payer
и обратное сохранение Client через реальный HTTP к локальному PocketBase.

Хеши изменённых файлов обновлены в `manager-live/MANIFEST.json`; исходные хеши
0.9.1 добавлены в список разрешённых предшественников для штатного обновления.
Новый номер релиза и готовый установщик этим аудитом не выпускаются.

## Что поправить дальше

1. **Принять два исправления менеджера и собрать отдельный патч-релиз.**
   Перед установкой сохранить штатную резервную копию и проверить именно
   удаление последних назначений и переключение Client/Payer на тестовых записях.
2. **Сделать сборку и проверку однозначными.** Сейчас `npm run build` собирает
   React 3.5, а не Classic; `package.json` тоже имеет версию 3.5.0. Добавить явные
   `build:classic`, `check:classic`, `check:manager`, затем CI на PR обеих веток.
   В текущих рабочих ветках нет `.github/workflows`; локальных проверок недостаточно
   для автоматической защиты следующих изменений.
3. **Зафиксировать общий выпуск и актуальную точку входа в документацию.**
   Указать пару SHA клиента/менеджера, версии hook-пакетов, результаты тестов,
   установку/откат. Старые `README`, `readmegpt.md` и документы от 08.10 содержат
   исторические модели; не использовать их без сверки с рабочими исходниками.
   Текстовое отсутствие конфликтов не заменяет испытание общего пакета.
4. **Закрыть проверку КИС перед расширением заказов.** По переданному контексту
   сохраняются вопрос получения прайса и прежнее несоответствие POST с ошибкой
   `aId_Clt`; владелец поставил разбор POST на паузу. Не подбирать поля запросом
   пробных записей. Возобновить после решения владельца и сверки с разработчиком КИС.
5. **Для внешнего рабочего запуска явно выключить тестовые входы на сервере.**
   Сейчас passwordless-демо — намеренная функция тестового контура. Скрытия кнопок
   недостаточно; приёмка рабочего контура должна проверить отключённые маршруты.

После стабилизации полезны журнал действий менеджера (кто и какие права изменил),
сохранённые шаблоны/черновики заказа с обязательной повторной проверкой прайса,
и отображение подтверждённого статуса заказа. Документы стоит подключать только
после согласования источника и правил доступа. Оптимизация шрифтов до WOFF2 —
необязательная задача: сейчас CSS Classic около 1,43 MB из-за встроенных TTF.
