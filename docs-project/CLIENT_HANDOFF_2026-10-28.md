# КАРАВАЙ — контекст клиентского кабинета

Срез: 28.10.2026. Репозиторий: https://github.com/nikitinad17-ai/Karavay_LK

Рабочая ветка: `feature/client-classic-orders-3.8`.
Проверенная версия: Classic 3.8.5, коммит
`9dbef2a767f67f6b6736ef6b0f7d84b96212c34d`.
Коммит опубликован. Установка этого выпуска на VM не подтверждена.
`main` и стандартная команда `npm run build` относятся к старому React 3.5.

## Где работать

- `src/classic/App.tsx` — интерфейс и сценарии кабинета.
- `src/classic/api.ts` — работа с сервером.
- `src/classic/repeatOrder.ts` — подготовка повторного заказа.
- `src/classic/bright.css`, `styles.css`, `fonts/` — оформление.
- `vite.classic.config.ts`, `scripts/build-classic.mjs` — сборка Classic.
- `classic-release/` — серверные обработчики, тесты и пакеты установки.

Шесть разделов сохраняются: обзор, оформление заказа, история, мои точки,
документы, профиль. Документы ещё не подключены. Вход использует общих
пользователей PocketBase; бизнес-доступ определяется активными правами,
покупателями и получателями через `/service/*`.

## Последние изменения

Вернулось яркое сине-жёлтое оформление с Ubuntu. Отдельный пакет стилей меняет
только согласованный CSS-блок существующего HTML.

Повтор заказа сопоставляет строки истории с текущим прайсом по коду товара.
Новый заказ использует текущие ID, цены и упаковку. Неоднозначные/недоступные
позиции показываются отдельно. Подготовка повтора не отправляет POST.
Нельзя терять защиту от устаревших ответов, незавершённой отправки и режим просмотра.

Три сценария v385: одна точка покупателя A; покупатель B минимум с двумя
проверенными активными получателями; покупатели C и B вместе. История и прайс
не блокируют создание тестовых входов. При отсутствии нужных точек нельзя
подставлять вымышленных получателей или объявлять сценарий готовым.

## Сохранить бизнес-правила

Отсутствующий/null/пустой минимум количества не равен числовому нулю:
для первого случая действуют полные лотки, заданный минимум допускает штуки.
Размер лотка должен быть валидным; количество POST выражается в штуках.
Подробности: `classic-release/QUANTITY-RULES.md`.

Повторно проверять прайс и количество на сервере перед отправкой. Не повторять
POST автоматически при неизвестном результате. Успех должен подтверждаться
ID заказа и последующим чтением его состава. Реальную историю не переписывать.

## Проверка и сборка

Команды выполняются в клиентской ветке, после `npm ci`:

```bash
npm run check
npx vite build --config vite.classic.config.ts
node scripts/build-classic.mjs
python3 classic-release/style-bright/test-style.py
python3 classic-release/order-repeat/test-update-client.py
python3 classic-release/test-access/test-scenarios.py
PB_BINARY=/path/to/pocketbase python3 classic-release/test-access/test-server.py
```

Проверено: 52 теста и TypeScript; отдельная сборка Classic/CSP; 5 тестов стилей,
9 обновления, 2 сценария; вход и откат на локальном PB. Chromium проверил
основные экраны, повтор и мобильную версию. Совместный вход из менеджера проверен
с собранным клиентом 3.8.5. КИС в этих проверках — фикстура.

Старый корневой E2E-набор ожидает демо 3.5 и сейчас не проходит. Нужен отдельный
набор Classic и явная команда/CI для него.

## Следующий шаг

Сначала зафиксировать способ сборки и текущие SHA, затем подтвердить установку
3.8.5 на VM. По переданному контексту прайс ещё требует проверки, а разбор POST
с `aId_Clt` поставлен владельцем на паузу. До возобновления не выполнять реальные
пробные заказы и не менять контракт КИС предположениями.

После исправления интеграции: шаблоны/черновики с пересчётом по актуальному прайсу,
понятные статусы заказа, затем документы при наличии серверного контракта.
Изменения менеджера согласовывать через его отдельную ветку; auth-роли
`owner/manager/viewer` не заменять клиентскими метками Client/Payer.
