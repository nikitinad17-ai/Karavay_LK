## Что установлено по коду репозитория

В [app/api.js](../app/api.js) обработчик `/api/login` сравнивает введённый пароль
со встроенными демонстрационными паролями. В [app/app.js](../app/app.js)
`login()` вызывает этот API, а `applyLoginResponse()` ожидает поля `role`, `payer`,
`client` и `enteredOutletId`. Результат PocketBase нужно будет адаптировать к этому
контракту либо осознанно изменить контракт интерфейса.

Есть отдельный сценарий: код точки и мастер-пароль её покупателя дают вход
покупателя на выбранную точку. Две отдельные auth-коллекции сами по себе не
описывают сохранение этого поведения. Его нужно подтвердить перед реализацией;
не восстанавливать его перебором демо-паролей в браузере.

Отдельных `authApi.js`, `pb_hooks`, `pb_migrations` и systemd-файла в исходниках
нет. Присланные примеры остаются документацией. В шаблоне есть внешние Google
Fonts: отсутствие интернета у VM не доказывает отсутствие интернета у браузера,
но при полностью автономном доступе шрифты следует доставлять локально.

## Что проверить в правах перед подключением интерфейса

По тексту миграции `updateRule` проверяет владельца записи, но не ограничивает
изменение `buyer`, `kis_code`, `active` и `must_change_password`. Это пробел
приведённой схемы, не подтверждённый взлом сервера: дополнительные серверные
настройки и hooks нам не переданы. Нужен явный перечень полей, доступных каждой роли.

`manageRule` даёт управление auth-записью, а не только сброс пароля.
В текущей документации доступны `@request.body.*` и ограничения через
`:changed`/`:isset`. Исправление `data` → `body` соответствует этой справке.
Проверки прав нужно выполнять обычными учётками: суперюзер обходит API rules.
[Источник: API rules](https://pocketbase.io/docs/api-rules-and-filters/).

В показанной миграции флаги `active` и `must_change_password` только объявлены;
условий их применения не показано. Значение BoolField по умолчанию — `false`.
Следовательно, выдача учётки должна явно задавать нужное состояние, а блокировка
и обязательная смена пароля требуют серверного поведения. Нельзя просто
блокировать весь вход до смены пароля: пользователю нужен ограниченный путь
для самой смены. [Источник: типы коллекций и полей](https://pocketbase.io/docs/collections/).

Для будущего прокси КИС нужен защищённый маршрут с проверкой пользователя и его
прав на конкретную точку/заказ. Документация показывает `$apis.requireAuth()` и
доступ к `e.auth`; сам факт размещения маршрута в PocketBase не задаёт бизнес-права.
[Источник: JS Routing](https://pocketbase.io/docs/js-routing/).

## Незакрытые решения

| Вопрос | Предложение для следующего этапа, ещё не реализовано |
| --- | --- |
| Кто задаёт `kis_code` и связь `buyer`? | Фиксировать сервером по подтверждённому соответствию; обычная точка не должна переносить себя к другому покупателю. |
| Кто меняет `active`? | Уточнить границы менеджера и покупателя; исключить самостоятельное снятие блокировки точкой. |
| Как исполняется `must_change_password`? | До смены разрешать только необходимые действия; снимать флаг после успешной смены на сервере. |
| Как выбирается коллекция при входе? | Определить по проверяемому правилу или серверному маршруту; префиксы демо-кодов не считать контрактом реальных кодов КИС. |
| Что делать при отказе PocketBase? | Показать ошибку и разрешить повтор. Автоматический вход по демо-паролям в рабочем режиме противоречит требованию серверной проверки. |
| Где брать данные после входа? | Согласовать серверное соответствие auth-записи покупателю/точке КИС. Вход сам по себе не заменяет загрузку данных. |
| Как восстанавливать доступ? | Начать с согласованной цепочки менеджер → покупатель → свои точки; контакты и OTP остаются открытым вопросом. |
| Нужны ли тестовые учётки? | Отдельные тестовые данные; старые демо-пароли не переносить в рабочие учётки по умолчанию. |

HTTP сохранён как временное решение пользователя; TLS здесь не настраивался.
Отсутствие исходящего интернета у VM не определяет её входящую доступность:
`0.0.0.0:8090` из unit означает прослушивание интерфейсов, а доступные подсети
зависят от сети и firewall. Их настройки не приложены. Автоматизацию загрузки
зависимостей из интернета нельзя считать рабочим способом установки на этой VM.

Утверждения конспекта о достаточности ресурсов для 600 точек и о 152-ФЗ
не превращены в проверенные выводы. Нагрузка, фактические CPU/RAM/диск,
резервное копирование и правовая оценка здесь не исследовались.

## Предлагаемая последовательность продолжения

1. Сопоставить фактический экспорт схемы и настроек auth с конспектом, сохранить
   конфигурацию без секретов и проверить восстановление резервной копии перед изменениями.
2. Уточнить матрицу прав и выполнить проверки: покупатель A/его точка/покупатель B,
   чужие записи, изменение служебных полей, блокировка, обязательная смена и сброс пароля.
3. Подключить `authApi.js` с согласованным контрактом, выходом и обработкой истечения
   доступа; проверить получение только разрешённых данных. Не добавлять демо-фолбэк.
4. Подготовить автономный комплект интерфейса, разместить на VM и проверить вход,
   роли и прежние сценарии интерфейса. Контракт КИС и TLS прорабатывать по фактическим данным.
