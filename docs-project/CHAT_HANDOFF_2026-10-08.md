## Что известно о внутреннем контуре

- VM PocketBase: `192.168.25.98`, HTTP `:8090`, админка `/_/`.
- HTML размещается в `pb_public`; локальный ЛК и PB API имеют один origin.
- По сообщениям владельца созданы `users`, `roles`, `rights`, `payers`, `clients`;
  проверены вход, смена пароля, выбор/переключение плательщика и active-флаги.
- Реальные matrix/orders из КИС успешным полным сценарием ещё не подтверждены.
- Пользовательские пароли принадлежат PocketBase, а не КИС. Новые учётные записи
  используют email; ранее принято требование обязательного email для восстановления.
- Административные проверки выполняются владельцем на Windows/VM по командам
  PowerShell. Рабочие файлы на Windows ранее находились в `Downloads`.
- Локальные проверки PB и связи с КИС могут выполняться без общего выхода VM в
  интернет, если доступны внутренний DNS и Web API. Внешний HTTPS-контур и доставка
  email требуют своей сетевой настройки; их готовность не подтверждена.
- Актуальная версия бинарника PB, экспорт коллекций/rules, текущий HTML VM и
  конфигурации reverse proxy/firewall в этой передаче отсутствуют.

## Решения из последнего обсуждения

Сначала обсуждался отдельный LK Gateway и внешний `/api/v1`. Последнее принятое
решение заменяет оба предположения:

1. Браузер вызывает `/service/context`, `/service/catalog`, `/service/orders`.
2. PocketBase на VM сам выполняет серверную логику шлюза через `pb_hooks`.
3. Авторизация — PB-токен; область данных — `rights → payer → client`, активная роль.
4. После проверки PocketBase обращается к `http://serv15db:55580/api/v1/...`.
5. Отдельный секретный ключ КИС не используется. PB-токен в КИС не передаётся.
6. Ответ проверяется/фильтруется на сервере и возвращается браузеру.
7. Сначала реализуется read-only каталог с результатами 401 / 403 / 200.

Имена `/service/*` остаются стабильными, если в будущем бизнес-логику перенесут в
отдельный шлюз. Само переименование пути не обеспечивает разграничения данных.

Ранние схемы с сервисным токеном, отдельным Gateway и внешним `/api/v1` сохраняются
как история; для следующей реализации руководствоваться текущим решением выше.
Российский VPS с WireGuard — вариант защищённого внешнего входа к внутренней VM,
а не решение переносить PocketBase и данные из сети КАРАВАЯ.

## Непроверенные вопросы и следующий этап

| Что надо установить | Зачем |
| --- | --- |
| Версия PocketBase и актуальный экспорт коллекций/rules | Написать hook под реальные API/relations, сохранить действующие данные |
| Какой HTML сейчас обслуживает VM | Связать пользовательскую проверку с конкретной версией |
| DNS `serv15db`, TCP 55580, запрос из VM без ключа | Проверить принятое условие доступа КИС |
| Реальный формат matrix, `DateOrd`, `Group` и IDs | Реализовать первый разрешённый read-only маршрут |
| Принадлежность заказа, write/cancel API и идемпотентность | Не угадывать контракт записи и не допустить дублей/чужих изменений |
| DNS публичного домена, сертификат и канал до VM | Выпустить внешний HTTPS-доступ при сохранении PB на VM |
| SMTP, письмо и ссылка восстановления | Подтвердить восстановление по email |

Следующая разработка: отдельная ветка для `GET /service/catalog`, проверка
user/role/right/payer/client, безопасные ошибки 502/504 и приёмка реального чтения.
Адаптация React к актуальным коллекциям выполняется отдельно, с сохранением шести
разделов, проверки заказа, нижней мобильной панели и защиты от гонок/дублей.

Рабочий процесс владельца: в чате администрирования PocketBase готовить схему,
проверки и задания; HTML/фронтенд изменять в отдельном процессе. Это обновление
сохраняет документацию; миграции, новые пользователи и серверные вызовы не выполнялись.
Обновление документации в GitHub прямо разрешено сообщением 2026-10-08; последующие
слияния runtime-веток и изменения боевой среды требуют своего задания.
