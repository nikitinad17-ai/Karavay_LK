# КАРАВАЙ — подключаемый кабинет менеджера 0.4

Подготовлен по четырём обработчикам, выгруженным 13.10.2026 с основной VM, и `pb_schema.json`. Адрес после установки: `/manager/` на том же PocketBase 0.40.3, origin `192.168.25.98:8090`. Это версия для приёмки: на VM ещё не установлена. Клиентский кабинет, прежние handlers и API rules не заменяются. Заказов в менеджерском интерфейсе нет. Приватный Site 0.3 остаётся отдельным локальным демо; на нём этот код не размещается.

## Возможности и область доступа

- Email/password через стандартную auth-коллекцию `users`; токен только sessionStorage, auth-refresh после F5, очистка при logout/401. Пароль не сохраняется.
- Менеджерский API допускает только активный `role_code=manager` с активной согласованной relation `role`. `owner` здесь означает пользователя покупателя, а не глобального администратора. Менеджеров создаёт администратор PocketBase; интерфейс создаёт только `owner/viewer`.
- Покупатели определяются активными `rights` менеджера. Отключённые покупатели остаются видны для административного включения. Чтение КИС и новые назначения требуют активного покупателя. Общее изменение покупателя разрешено только менеджеру с `scope=all`.
- Пользователи могут иметь несколько покупателей и отдельные получатели. Учётные записи с любыми, включая отключённые, назначениями вне области менеджера можно видеть в своей области, но нельзя менять или сбрасывать им пароль. Самого менеджера и других менеджеров изменять нельзя.
- Создание пользователя требует `name`, `email`, `login`, выбранную активную роль и хотя бы одно назначение. relation `role` и `role_code` записываются согласованно. Сохранение пользователя и прав выполняется одной транзакцией.
- Временный пароль от 12 символов задаёт менеджер. `must_change_password=true`. Новый пользователь открывает `/manager/`, входит и меняет пароль. После смены нужно войти заново в клиентский кабинет `/`. Этот маршрут смены доступен авторизованным пользователям, даже если дальнейшая работа заблокирована обязательной сменой пароля. Клиентский HTML 3.7.1 этим пакетом не меняется.
- Получатели выбираются из КИС через PB, а не создаются в КИС. При выборе сервер проверяет детали, принадлежность покупателю и `state=1` (это действующее предположение прежних hooks, значение требует бизнес-подтверждения). Каталог кандидатов может содержать неактивные точки: при подключении они отклоняются.
- Подключение получателя создаёт или обновляет локальную совместимую карточку `clients` с данными КИС. Новые адресные права содержат и `scope/kis_client_id`, и соответствующий `rights.client`. Это сохраняет уникальность старого индекса `(user,payer,client)` и позволяет нескольким адресным правам существовать без миграции. Gateway продолжает использовать `scope/kis_client_id`. Нельзя перепривязать локальную карточку к другому покупателю. Локальный `clients.active` не управляет активностью точки в КИС; интерфейс не предлагает такую кнопку.
- Добавление покупателя — регистрация **ранее не привязанного** числового КИС ID в PocketBase, проверяемого через известные `/payers/{id}/clients` и `/clients/{id}`. Требуется хотя бы один активный получатель для проверки. Код, название и контакты покупателя вводит менеджер: endpoint карточки самого покупателя в переданных hooks не подтверждён. КИС не изменяется. Покупатель назначается создавшему менеджеру. Если этот ID/код уже зарегистрирован, создание отклоняется; присоединить себе чужую запись этим действием нельзя. Назначение существующего покупателя менеджеру выполняет администратор. Менеджер с этой ролью имеет право подключать новых покупателей; перед приёмкой подтвердить это правило у владельца, если должностные полномочия ограничены.
- Сброс отправляет реальное письмо через `$mails.sendRecordPasswordReset`. Ответ означает передачу почтовому сервису, а не доставку. Native confirm-password-reset снимает `must_change_password` после подтверждения. При неработающем SMTP возвращается ошибка. Ссылку и фактическую доставку проверяют отдельно на VM; конфигурация SMTP не меняется.
- Изменения логируются в серверный журнал (`manager.mutation`, `manager.reset_password`), без паролей и токенов. UI отдельного журнала пока нет.

## Контракт

| Маршрут | Назначение |
|---|---|
| `GET /service/manager/state` | Менеджер, назначенные покупатели, пользователи и права в области |
| `GET /service/manager/clients?payer=<PB ID>` | Кандидаты КИС для выбранного покупателя |
| `POST /service/manager/action` | `create_user`, `edit_user`, `set_rights`, `toggle_user`, `reset_password`, `create_payer`, `edit_payer`, `attach_client` |
| `POST /service/account/change-password` | `{oldPassword,password}`; смена пароля и обязательный повторный вход |

Business-параметры проходят проверку на сервере. КИС вызывается с фиксированным host через `curl`, как в установленном gateway. PB-токен не передаётся в КИС. Для исходящих запросов действуют таймаут и ограничение размера, redirect запрещён. Внешние URL и детали исключений не выдаются браузеру. Запись users/rights/clients выполняется в транзакции с повторной проверкой менеджера. Сетевые вызовы выполняются до транзакции.

## Проверки

Пройдена 41 HTTP-проверка и 8 проверок интерфейса через jsdom с реальными HTTP-запросами к локальному PB. Проверена передача письма локальному тестовому SMTP и подтверждение сброса стандартным PB API. Визуальный прогон браузера не выполнен: скачивание Chromium завершилось повреждённым архивом. Установщик синтаксически проверен; реальная установка/откат службы на VM ещё не выполнялись.

`node --check` для серверного и браузерного JS. HTTP-интеграция: изолированный PocketBase **0.40.3**, структура пяти коллекций из присланного экспорта, новые синтетические записи и локальная заглушка `curl`/КИС. Команда:

```sh
PB_BINARY=/path/to/pocketbase python3 manager-live/tests/integration.py
```

Для DOM-проверок используется `jsdom` из зависимостей корневого проекта (после `npm ci`).

`tests/schema.json` содержит только определения пяти коллекций для тестов, не пользовательские записи, пароли или SMTP настройки. Тест запускает свой PB на `127.0.0.1:18943`, временные данные удаляются. Тесты не обращаются к VM или КИС. Бинарник для тестов скачивается отдельно с официального релиза PocketBase 0.40.3. Установщик не меняет бинарник.

На VM обязательна отдельная приёмка: вход менеджера, создание трёх сущностей, два получателя одному пользователю, блокировки чужих IDs/неактивности/общей учётной записи, F5/logout, временный пароль, SMTP и клиентский `/` после изменений. Скорость загрузки реальных 600+ точек нужно измерить; в этой версии кандидаты читаются целиком (лимит 2000), с поиском в браузере. Внешний HTTPS-контур этим пакетом не настраивается.

## Установка

Пакет не содержит миграций и не открывает прямую запись в коллекции. Установщик проверяет hashes четырёх действующих hooks, имена/типы обязательных полей и версию PB. Он откажется работать, если исходники VM изменились с момента выгрузки. Файлы `karavay-manager.js` и `karavay-manager.pb.js` добавляются в `pb_hooks`, интерфейс — в `pb_public/manager`.

После копирования распакованного `manager-live` на VM в `/home/lindevadmin/manager-live` выполнить сначала только проверку:

```sh
sudo python3 /home/lindevadmin/manager-live/scripts/install.py
```

Она не меняет сервер. После успешной проверки установить отдельной командой:

```sh
sudo python3 /home/lindevadmin/manager-live/scripts/install.py --install
```

При установке PocketBase кратко останавливается, `pb_data` копируется в каталог `/opt/.karavay-manager-before-<время>` с доступом только root, добавляются файлы и служба запускается. Проверяются health, 401 без авторизации и HTML менеджера. При неуспешном smoke новые файлы автоматически удаляются/восстанавливаются и служба запускается. База не заменяется из резервной копии: пакет не изменяет схему или записи при установке. Последующие действия в менеджерском UI пишут настоящие данные. Smoke не заменяет приёмку обычным менеджерским пользователем.

## Подготовка с Windows

`scripts/Download-Karavay-Manager.ps1` скачивает только необходимые файлы и проверяет SHA256 по манифесту, создаёт ZIP в Downloads. С ключом `-CopyToVM` копирует каталог по SSH и запускает только read-only preflight. Установку он автоматически не запускает; печатает отдельную точную команду. SSH/sudo-пароли вводятся только в терминале. На Windows скрипт пока не запускался.

## Назначение первого покупателя менеджеру

`Grant-Manager-Access.py` запускается на VM через интерактивный `ssh -t`, без sudo. По умолчанию находит существующего пользователя с `login=manager_test` и покупателя с `kod_pay=A120`. Учётные данные `_superusers` вводятся в терминале через prompt/getpass; пароль не хранится и не выводится. API используется только по loopback `127.0.0.1:8090`, без environment proxy. Подтверждённое активное право `all/0` используется повторно; отключённое включается, отсутствующее создаётся. Пароли, users/roles, прежние права других пользователей и схема не изменяются. Старые конфликтующие записи не исправляются автоматически. После записи выполняется повторное чтение права. На реальной VM этот скрипт ещё не запускался.

```sh
python3 /home/lindevadmin/Grant-Manager-Access.py
```

Для другой пары используются `--manager-login <login>` и `--payer-code <kod_pay>`. Первые шесть дополнительных интеграционных проверок проверяют создание, повторный запуск, реактивацию и отказы при неизвестном логине, покупателе и недопустимой роли.
