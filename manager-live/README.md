Дата: 14.10.2026. Рабочая ветка: feature/manager-cabinet-v0.3.
Основа: 0.7.0; допустимо обновление с известных выпусков 0.6.x. Установку 0.7.1 на реальной VM пользователь пока не подтвердил.

## Таблица пользователей — интерфейс от 16.10.2026

Визуальный ориентир — предоставленный `1(1).PNG`: синяя полоса фильтра роли,
жёлтая кнопка «Создать пользователя», отдельные колонки логина/имени, email,
роли, статуса, покупателей и получателей с кодами, видимые действия справа.
Фильтр роли работает вместе с поиском; счётчик показывает число найденных записей.
«Инфо» открывает сведения без возможности записи. Создание и отдельное окно
назначений сохранены. На узком экране колонки располагаются внутри строки
вертикально; навигация переносится без расширения страницы.

Используется действующая модель ролей owner/viewer и прежняя область менеджера.
Вместо «Подтверждён» показан статус аккаунта: текущий state не передаёт verified.
Вместо удаления доступно существующее отключение. Общий серверный контракт,
hooks, миграции и клиентский кабинет не меняются.

Названия покупателей уже присутствуют в state. Для конкретных получателей сначала
видны их реальные КИС ID; «Показать коды и названия» читает существующий маршрут
clients только для покупателей этой строки и выводит лишь назначенных получателей.
Начальное открытие таблицы не обходит получателей всех покупателей. Ошибка запроса
показана с возможностью повторить; устаревший ответ после обновления state или
выхода отбрасывается. Все получатели общего права обозначены явно.

Это правка интерфейса поверх 0.7.1, не независимый выпуск общего сервера.
MANIFEST содержит актуальные hashes и допускает обновление известных файлов 0.7.1.
Прежний ZIP от 14 октября не содержит эту таблицу. По указанию Алекса от 16 октября
установка продолжается здесь, в чате менеджера, с сохранением клиента 3.8.0.

Проверено 16 октября: 70 HTTP-проверок на отдельном PB 0.40.3 с заглушкой КИС,
18 проверок интерфейса через локальный HTTP и 16 проверок сессии/загрузки названий
(включая повторный вход после выхода, ошибку КИС, повтор и поздние ответы).
Chromium: таблица и создание пользователя при ширине 1680 и 390 px, фильтр роли,
«Инфо», названия получателей, отсутствие горизонтального выхода страницы.
`npm run check`: типы, 22 теста и production build прошли.

Отдельный старый React E2E-набор клиента: 1 passed, 1 skipped, 6 failed на demo-сборке.
Два desktop-сценария останавливаются на неоднозначных локаторах, четыре mobile —

## Поведение

1. «Добавить пользователя»: имя, email, технический логин, роль, временный пароль.
2. Сохранение создаёт учётную запись без бизнес-прав. Она видна создавшему её
   менеджеру со статусом «Ожидает назначения», включая повторный вход и F5.
3. Автоматически открывается отдельное окно «Покупатели и получатели» со всем
   справочником КИС, поиском и галочками. Получатели читаются только для отмеченных
   покупателей. Область — все получатели либо несколько выбранных.
4. Сохранение доступа атомарно создаёт нужные новые связи КИС → PB и права.
   Не нужны отдельные команды или обязательный контактный email покупателя.
5. Закрытие второго окна оставляет пользователя без прав, назначения можно продолжить
   кнопкой в его строке. Снятие всех назначений требует подтверждения.

Пользователи представлены аккуратными строками: имя, email, логин, роль, коды
покупателей, область доступа, действия. Покупатели — список кода/названия/email
(если он есть у доступного менеджеру покупателя), без карточек. Синий заголовок
окна и компактный выбор сделаны по скриншоту Снимок(20261014-160616).PNG.
Предпочтение галочек из localStorage версии 0.6.2 больше не ограничивает выбор:
источник истины — назначения конкретного пользователя, полученные с сервера.

## Сохранение входа — 0.7.1

На форме входа появилась галочка «Запомнить меня на этом компьютере» (по умолчанию
снята). При её выборе сохраняется только токен PocketBase в localStorage; пароль
в браузерное хранилище не записывается. Без галочки остаётся sessionStorage.
Повторное открытие вкладки/браузера и F5 проверяют токен через users/auth-refresh,
затем заново загружают права. Истёкший/отозванный токен требует обычного входа;
срок действия токена в PocketBase не увеличивается. Долгий перерыв после истечения
токена не может восстанавливать доступ автоматически.

«Выйти» очищает сохранённый вход и передаёт выход другим вкладкам менеджера.
401 и запрет доступа в manager/state очищают вход. Сетевой сбой/5xx при восстановлении
сохраняет токен и показывает кнопку повтора. Ответ, пришедший после выхода,
не восстанавливает сессию. При обязательной смене пароля открывается прежнее окно.
Личный кабинет клиента в этом пакете не изменяется.

Уточнение от 14.10: SSH-пароли и ключи не относятся к этому требованию.
Setup-Karavay-SSH.ps1 удалён из текущего пакета, установщик использует обычные ssh/scp.

## Данные и доступ

- Добавляется единственное необязательное скрытое поле users.manager_owner,
  relation → users. Оно связывает пользователя без прав с управляющим менеджером.
- Владение не даёт права редактировать пользователя с назначениями вне области
  менеджера, включая неактивные назначения. Общие аккаунты остаются read-only.
- Новый не зарегистрированный в PB покупатель доступен для назначения напрямую
  из КИС. Существующий чужой покупатель виден в справочнике с заблокированной
  галочкой; его доступ назначает администратор. Захвата чужих PB-записей нет.
- Отсутствие бизнес-прав не открывает данные клиента даже после смены пароля.
- manager_owner устанавливается сервером, подмена через native API запрещена.
- Отдельная форма «Добавить покупателя» сохранена для совместимости. Для назначения
  из нового окна она не нужна; контактный email новой записи покупателя остаётся
  пустым, вымышленную пользовательскую почту туда не копируем.
- Реальные названия/коды/ID берутся из КИС, принадлежность и активность выбранного
  получателя проверяются при сохранении. КИС вызывается только GET.
- КИС не используется для авторизации. Пользователи/пароли/права находятся в PB.
- Коды бизнес-ролей owner/viewer/manager не переименованы под старый скриншот.

## API

GET /service/manager/state — свои покупатели, доступные аккаунты и свои черновики.
GET /service/manager/directory — минимальный общий справочник покупателей КИС.
GET /service/manager/clients?payer=<PB ID> — получатели в области менеджера.
GET /service/manager/kis-clients?payer=<KIS ID> — получатели нового покупателя КИС;
если покупатель уже зарегистрирован, проверяются существующие менеджерские права.
POST /service/manager/action:
- create_user теперь допускает отсутствие rights; старый вызов с rights поддержан.
- set_rights допускает пустой массив (полное снятие) и массив назначений с payer
  либо kis_payer_id (ровно один идентификатор), scope, kis_client_id.
- Остальные действия совместимы с 0.6.2.

## Установка

По указанию Алекса от 16 октября установка продолжается в этом чате менеджера.
Актуальный `scripts/Download-Karavay-Manager.ps1` скачивает файлы из одного
точного Git-коммита в обычный Windows Downloads, проверяет SHA-256, копирует
пакет на VM и запускает проверку совместимости и установку через sudo.
Окно выбора файла не используется. Старый ZIP от 14 октября для новой таблицы
не подходит.

Настройка SSH-ключей не нужна. Пароли VM и кабинета не меняются. Запрос пользователя
«сохранить пароль» относится к сохранению входа в кабинет менеджера.

Обычный PowerShell, после скачивания скрипта из того же точного коммита:

```powershell
.\Download-Karavay-Manager.ps1 -SourceRevision <полный-SHA-коммита> -Install
```

`-CopyToVM` вместо `-Install` выполняет только копирование и read-only preflight.
Без обоих ключей создаётся локальный проверенный пакет. Для `-Install` обязателен
полный SHA; ветка не используется как меняющийся источник во время установки.
Демо-скрипт новым установочным путём не запускается.

Установщик проверяет PB 0.40.3, схему, известные hashes предыдущих менеджеров и
существующего шлюза, включая проверенный orders-handler клиента 3.8.0. Чужие
неприменённые миграции останавливают установку до изменений. После остановки
службы создаётся полный закрытый backup
pb_data и заменяемых файлов. Устанавливаются только менеджер и одна добавочная
миграция, применяемая PocketBase при старте. Основной HTML клиента, gateway,
пароли, текущие роли/права не перезаписываются. При сбое восстанавливаются файлы;
добавочное поле может остаться, snapshot базы сохраняется для ручного восстановления.

После запуска проверяются точный HTML новой таблицы, hashes файлов менеджера,
закрытые маршруты и неизменность клиентского HTML и прочих handlers.
Маркер успеха: `MANAGER_TABLE_INSTALLED: users-table-20261016` и строка `BACKUP:`.
Затем открыть /manager/ и нажать Ctrl+Shift+R. Основной клиент 3.8.0 сохраняется.

Локальная проверка установщика: `python3 manager-live/tests/installer.py`.
Она использует отдельную SQLite-схему и имитацию systemd, проверяет совместимые
hashes, отказ неизвестным файлам/миграциям и отсутствие записи при preflight.
PowerShell и установка на реальную VM в этой среде не выполнялись.

## Два пользователя (демо)

scripts/Create-Demo-Users.py запускается на VM, спрашивает email/пароль менеджера
один раз. Получает актуальный справочник КИС и два доступных покупателя с получателями:

- Один покупатель (демо): owner, один покупатель, один конкретный получатель.
- Несколько покупателей (демо): viewer, два покупателя, по одному получателю.

Вымышленные адреса demo.single.<manager ID>@example.test и
 demo.multi.<manager ID>@example.test. Письма не отправляются. Случайные временные
пароли сохраняются только в ~/karavay-demo-access-<manager ID>.json с mode 0600;
в журнал и GitHub не попадают. Секреты не присылать в чат. При первом входе сменить
пароль через /manager/, затем открыть клиентский кабинет /.

Повторный запуск сохраняет готовые учётные записи и пароли; после частичного сбоя
может продолжить свой черновик. Реальная активность получателей окончательно
проверяется сервером при сохранении; если КИС не подтверждает выбранного получателя,
скрипт останавливается, пользователь остаётся без неподтверждённых прав. Назначения
можно завершить в интерфейсе. На VM эти аккаунты ещё НЕ созданы до запуска скрипта.

В соседней ветке classic 3.8 есть отдельный Seed-Demo-Users.py с другими адресами.
Для этой приёмки используйте один этот скрипт, чтобы не заводить лишние тестовые
учётные записи. Ни один из шагов этого пакета не создаёт заказы.
