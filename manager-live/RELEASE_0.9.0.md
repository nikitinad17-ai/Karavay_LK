# Менеджер 0.9.0 — отдельные входы покупателей и получателей

Дата: 27.10.2026. База: менеджер 0.8.1 (`02a4821`).
Рабочая ветка: `feature/manager-cabinet-v0.3`.

## Разбор проблемы

В форме и таблице код роли `owner` назывался «Покупатель». Поэтому пользователь,
ограниченный одной торговой точкой, также выглядел как покупатель. Роль определяет
возможность оформления заказа; область покупатель/получатель определяется правами.
`viewer` означает только чтение и не является ролью получателя.

Названия организации и точки могут совпадать в КИС. Приложение не должно заменять
их выдуманными названиями: различать нужно код, адрес и родительского покупателя.
Ранее таблица скрывала адреса, а общее право показывала только как «Все получатели».

Старый полный установщик закреплял покупателей 2/3 — производителей «Каравай» и
«Паляница». Это противоречило уточнению владельца. Новый сценарий не использует
старый приватный план, прежние пароли или конфигурацию клиентского тестового входа.

## Результат

- Возможности: «Оформление заказов» / «Только просмотр», реальные коды ролей сохранены.
- В таблице отдельно видны «Покупатель · все получатели», «Получатель · одна точка»,
  «Выбранные получатели» или «Несколько покупателей».
- Получатели отображаются с собственным кодом и адресом. Для общего права можно
  раскрыть реальные точки; название покупателя не подставляется вместо получателя.
- В разделе получателей кнопка «Создать вход получателя» сохраняет контекст точки
  в первом окне и отмечает только её во втором окне назначения прав.
- «Демо-пользователи»: две группы по покупателю, в каждой вход покупателя и два
  отдельных входа его получателей. Каждый открывает обычный кабинет клиента в
  отдельной вкладке без ввода пароля. Сессия менеджера остаётся в своей вкладке.

## Подбор и создание демо

`Setup-Recipient-Demos.py` на VM читает текущий КИС: `/payers`, карточки покупателей,
их `/clients` и карточки точек. Нужны два разных допустимых покупателя, у каждого
минимум два активных получателя с кодами и адресами. Проверяются принадлежность
и действующие связи PocketBase. Известные производители и отклонённые прежние
демо исключены по ID и названию. Кодовый префикс не используется как признак типа
организации: такого признака доступный контракт КИС не предоставляет.

Не найден полный набор — до записей остановка, без сценария с одной точкой и
без подстановки производителей. Прайс и история не являются условием создания
пользователей, `/orders` и запись в КИС не вызываются. Наличие истории не обещается.
Реальные названия выбранных организаций известны только после запуска на VM.

Создаются шесть `users`, шесть их `rights`, недостающие проверенные сопоставления
`payers/clients` и права менеджера только на вновь подключённые компании. Для уже
зарегистрированной компании необходимо существующее общее право этого менеджера;
чужую область скрипт не присваивает. Каждый пользователь имеет собственный случайный
пароль, сгенерированный внутри PocketBase; исходные пароли не записываются в файлы
и не передаются в браузер. Почта `example.test` применяется только к новым демо.
Имена, контакты и пароли существующих пользователей не перезаписываются.

Модель `users/roles/rights/payers/clients` сохранена. Миграция демо транзакционно
добавляет данные, структура коллекций не меняется. Поле `manager_owner` уже есть
при установленном 0.8.1; прежняя аддитивная миграция менеджера сохранена.
Повтор использует сохранённые ID, не создаёт дубли и не сбрасывает пароли.
Отключённые/изменённые аккаунты и права автоматически не восстанавливаются.

## Тестовые входы

Новые GET `/service/manager/demo-accounts` и POST `/service/manager/demo-login`
требуют обычного действующего менеджера, фиксированной локальной конфигурации,
его доступа к компании и точного совпадения демо-аккаунта/прав. POST принимает
только ID одного из шести аккаунтов и требует совпадающий Origin. Выбрать менеджера,
суперпользователя или произвольного клиента нельзя. Ответы не кэшируются.
Вход выдаёт обычный пользовательский токен; все клиентские `/service/*` проверки
сохраняются. Пароли и токены не включаются в публичный список демо.

Клиентский HTML не заменяется; используется существующая сессия клиента 3.8.x.
Конфигурация `/service/test-access` другого клиентского выпуска остаётся прежней.
Новые входы находятся в менеджере `/manager/`, вкладка «Демо-пользователи».
Приватный `file://` менеджер сохраняет прежние функции; новые входы открываются
с серверной страницы менеджера. Фирменная тема и логотип не изменены.

## Установка

Скачать `Karavay-Manager-0.9.0-Recipients-20261027.ps1` в Downloads. Выполнить в
**Windows PowerShell**:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\Downloads\Karavay-Manager-0.9.0-Recipients-20261027.ps1"
```

Пакет самодостаточный; VM не скачивает исходники из интернета. Нужны обычные
SSH/sudo на VM, пароль админки PB не требуется. Сначала устанавливаются файлы
менеджера с резервной копией, затем включается его тестовая кнопка и выполняется
настройка демо. Перед записью данных создаётся отдельная резервная копия `pb_data`.
Схема, версия и известные хэши проверяются до установки. Клиент, gateway и
конфигурация другого тестового входа сохраняются.

Успех: `MANAGER_RELEASE_INSTALLED: 0.9.0`, затем `RECIPIENT_DEMOS_READY: 6`.
Открыть `http://192.168.25.98:8090/manager/`, обновить Ctrl+F5, нажать
«Тестовый вход менеджера», открыть «Демо-пользователи».

`-PreflightOnly` проверяет установку без изменений. `-TestLoginOnly` устанавливает
менеджера и включает его кнопку без создания демо. `-ResumeSetup` продолжает только
настройку после уже установленного 0.9.0. После сбоя повторяется тот же пакет:
не нужно удалять план, менять пароли или создавать пользователей вручную.

## Проверки и границы

Пройдено:

- `npm run check`: TypeScript, 22 теста, сборка.
- 70 HTTP-проверок менеджера с настоящим локальным PB 0.40.3, 18 проверок
  двухэтапного создания и назначений через jsdom/PB HTTP, 16 проверок сессии.
- 8 проверок установки, включая частичную запись и откат файлов.
- 14 запусков настоящего PowerShell 7.4.6/Linux с Legacy native argv, пробелами
  в пути профиля и фикстурами SSH/SCP: полный/resume/preflight/test-only,
  отказы копирования, SSH и настройки, запрет несовместимых опций.
- Реальный отдельный PB: подбор двух компаний с несколькими точками,
  шесть отдельных аккаунтов, повтор без дублей/смены паролей, сохранение прежних
  пользователей и клиентской конфигурации, отказ при недостаточном наборе,
  область менеджера, Origin, самостоятельный пароль получателя, запрет
  повторного включения отключённого аккаунта.
- Chromium headless 134 + настоящий PB + собранный неизменённый клиент 3.8.2
  (`a56ad6a`): шесть входов в отдельных вкладках, реальные списки разрешённых
  получателей, F5/logout, сохранение сессии менеджера, адреса/подписи, создание
  обычного пользователя из строки точки с одним назначением, мобильный экран.
- Прежний private/public менеджер: реальная авторизация, статический токен 8 ч,
  logout, роли/активность/обязательная смена пароля, CSP/личные файлы и отсутствие
  дублей. Исторические тестовые сценарии теперь используют фикстуры 22/23,
  производители 2/3 исключены также из старого provisioner.

Браузерная проверка выявила конфликт имён: прежняя функция модальной формы
`open` перекрывала встроенный `window.open`. Форма переименована в `openEditor`;
переходы во вкладки проверены фактически, остальные модальные формы сохранены.
Тема и логотип побайтово совпадают с 0.8.1.

КИС/системная служба в тестах являются локальными фикстурами. Результаты не
доказывают доступ к VM или фактический подбор покупателей в её КИС.
Windows PowerShell 5.1 нативно не запускался. Автоматической установки на
внутреннюю VM из среды разработки нет. Команды воспроизведения — в README.
