- `feature/v3.6-user-multi-buyer-auth` содержит React 3.6 на ранней схеме

- Рабочий standalone 3.6.3 сохранён в `feature/v3.6.4-demo-showcase`; он использует

- Demo Showcase 3.6.4 подключён к PB для прав, но бизнес-данные локальные.
  Не считать его успешным подключением реальных matrix/orders.

  текущей модели требует изменения типов/адаптера/прав/тестов, а не env-переименования.

## Последняя согласованная схема КИС

- PocketBase остаётся на VM `192.168.25.98:8090` и сам выполняет роль шлюза
  через `pb_hooks/*.pb.js`.
- Публичные бизнес-пути: `/service/context`, `/service/catalog`, `/service/orders`.
- PocketBase проверяет user/role/right/payer/client и вызывает внутренний
  `http://serv15db:55580/api/v1`. Браузер этот upstream не вызывает.
- Отдельный ключ/сервисный токен КИС не используется. PB-токен туда не передаётся.
  Доступ КИС без ключа ещё надо подтвердить именно с VM; отказ 401/403 не скрывать.
- Внешний origin использует HTTPS; публичный reverse proxy соединяется с VM
  через защищённый канал. VPS/WireGuard и `lk.karavay.spb.ru` пока являются
  вариантом/целевым адресом, а не подтверждённой публикацией.
- Первый этап: `GET /service/catalog`, результаты 401 / 403 / 200; затем чтение
  заказов, после него отдельное согласование записи и отмены.
- Ошибки КИС: безопасные 502/504, без mock fallback и внутренних URL в ответе.
- Нативные PB auth-маршруты `/api/collections/users/*` сохраняются. Ограничение
  относится к внешнему `/api/v1`, а не ко всем путям `/api/*`.

## Доступ и сессия

- Вход только пользователя из `users`, по email в рабочем standalone.
- Роль существует, активна и имеет известный code: owner / manager / viewer.
- Активное право с пустым client открывает всех активных clients одного payer;
  иначе доступны только конкретные clients из активных rights.
- Нет прав или неактивное звено — нет бизнес-доступа и демо-подстановок.
- requireAuth подтверждает вход; область прав проверяется отдельно на сервере.
- API rules для прямых запросов PocketBase также должны исключать чужие данные.
- Один payer выбирается автоматически; несколько показывают выбор.
- F5: auth-refresh + повторная загрузка роли/прав; logout очищает сессию и контекст.
- При смене payer очистить зависимые данные, подтвердить потерю правок и отсечь
  устаревшие ответы. Токен — только sessionStorage, пароль не сохранять.
- Email обязателен для восстановления; SMTP/доставку и ссылку сброса проверять отдельно.

## Неизменные бизнес-ограничения

- Сохранять шесть разделов: обзор, заказ, история, получатели, документы, профиль.
- Покупатель/плательщик управляет своими получателями; ориентир — около 600 точек.
- Заказ проходит явную проверку; мобильная нижняя панель сохраняется.
- Единые минимум SKU и кратность полного лотка для lotOnly — в UI и API.
- Ошибка API не уничтожает корзину и правки; двойная отправка блокируется.
- Не мутировать заказы/кэши, сверять поколение асинхронного запроса.
- TypeScript strict; не использовать any, @ts-ignore, @ts-nocheck для обхода типов.
- Публичные ресурсы используют import.meta.env.BASE_URL; историческая React-сборка
  имеет base `/react-test/`, standalone для pb_public — свой способ размещения.

## Проверка и передача

1. Сверить версию PB, экспорт коллекций/rules и текущий HTML VM перед миграциями.
2. По изменениям исходников выполнить `npm run check`; при доступном Chromium —
   `npm run test:e2e`. Для документации проверить ссылки, схемы и статусы.
3. Проверять чужие ID обычным токеном, отключение active после входа, one/multi/
   no-access, F5, logout и переключение payer.
4. Обновить текущий контекст и пометить фактически выполненные проверки.
5. Не коммитить пароли, токены, pb_data, node_modules и dist.

В чате администрирования PB готовить схему, команды проверки и задания для
фронтенда; HTML изменяется в отдельном процессе. Если команды выполняет владелец,
давать по одному проверяемому шагу и ждать результат. Следующие runtime-слияния и
изменения боевой VM должны иметь отдельное задание; перенос документации в GitHub
разрешён текущим сообщением владельца.
