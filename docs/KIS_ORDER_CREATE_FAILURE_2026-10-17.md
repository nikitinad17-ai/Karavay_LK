# КИС: отказ создания заказа при документированном Id_clt

Дата проверки: 17.10.2026. Контур: тестовая КИС. Источник результата — запуск
владельцем контрольного скрипта на VM и полный сохранённый JSON, предоставленный
владельцем в чате. Независимого подключения к VM из облачной среды нет.

## Подтверждённое поведение

Прямой запрос с VM к `http://serv15db:55580/api/v1/orders`:

```http
POST /api/v1/orders
Content-Type: application/json
Accept: application/json
```

```json
{
  "Id_clt": 2,
  "DateOrd": 1792270800,
  "Product": [{"Id_prd": 203080, "KolSht": 1}]
}
```

Дата заказа — 18.10.2026, 00:00 Europe/Moscow. Одна позиция из фактической
датированной матрицы получателя 2, сумма 27.40, minimum_sum=0. Текущий OpenAPI,
прочитанный с той же VM, описывает `Id_clt`, `DateOrd`, `Product`, `Id_prd`,
`KolSht`. Python отправляет JSON напрямую; PocketBase не выполняет этот POST,
PB-токен в КИС не передаётся.

Фактический ответ — **HTTP 400**:

```json
{
  "success": false,
  "error": {
    "message": "Не задан aId_Clt",
    "code": "-20001",
    "details": "ORA-06512: на  \"KRDEV.RAISE_I\", line 15\nORA-06512: на  \"DBTFOTG.PKG_HOP\", line 59\nORA-06512: на  \"DBAPI.PKG_REST_H_ORDERS\", line 100\nORA-06512: на  \"DBAPI.PKG_REST_H_ORDERS\", line 239\nORA-06512: на  line 1\nORA-06512: на  \"DBAPI.PKG_REST_ROUTE\", line 179\nORA-06512: на  \"DBAPI.PKG_REST_I\", line 49\n"
  }
}
```

Контрольное состояние `rejected`, `id=null` сохранено на VM в
`/home/lindevadmin/karavay-control-order-test381point001.json`. Повторный запуск
остановился с `NO_REPEAT_POST` без новой отправки. Успешное создание заказа
не подтверждено; проверка нового заказа в истории не выполнялась. Этот отказ
не объясняет сам по себе пустоту старой истории других получателей.

## Что нужно проверить в КИС

Стек подтверждает исключение в PL/SQL-обработке КИС. Точная причина по одному
стеку неизвестна. Возможное место проверки — чтение JSON `Id_clt` и передача
полученного значения во внутренний параметр `aId_Clt`; это гипотеза, не готовый
диагноз и не основание переименовывать поле HTTP-запроса в `aId_Clt`.

Нужны исходники из **той базы/редакции, которую использует этот API**:

| Объект | Нужные строки PACKAGE BODY | Цель просмотра |
| --- | --- | --- |
| `DBAPI.PKG_REST_H_ORDERS` | 1–120 и 210–255 | Чтение JSON, параметры вызова, ветка POST около 100/239 |
| `DBTFOTG.PKG_HOP` | 1–85 | Сигнатура процедуры и проверка около строки 59 |

Если фрагменты не включают объявление вызванной процедуры/парсер, потребуется
соответствующее объявление или полное тело пакета. В репозитории LK этих
исходников нет; изменение клиентского HTML не исправляет PL/SQL-код.

Запрос ниже выполняется в SQL Developer/SQLcl под существующей учётной записью,
которая имеет доступ к исходникам. Это только SELECT, без вызова процедуры
создания заказа и без изменения объектов/данных:

```sql
SELECT owner, name, type, line, text
FROM all_source
WHERE type = 'PACKAGE BODY'
  AND (
    (owner = 'DBAPI' AND name = 'PKG_REST_H_ORDERS'
      AND (line BETWEEN 1 AND 120 OR line BETWEEN 210 AND 255))
    OR
    (owner = 'DBTFOTG' AND name = 'PKG_HOP'
      AND line BETWEEN 1 AND 85)
  )
ORDER BY owner, name, line;
```

`ALL_SOURCE` показывает доступные текущему пользователю исходники; пустой
результат не доказывает отсутствие пакета. SQL не запускался в базе КИС в этой
среде. Состав колонок и тип `PACKAGE BODY` сверены с официальной документацией
[Oracle ALL_SOURCE](https://docs.oracle.com/en/database/oracle/oracle-database/26/refrn/ALL_SOURCE.html).
Если тело wrapped или недоступно, нужен незашифрованный исходник от разработчика
КИС. Пароли, строки подключения и ключи передавать не нужно.

## Критерий исправления

1. По исходнику установить, какое значение дошло до проверки и почему.
   Привести фактическую обработку и опубликованный контракт к согласованному виду.
   Если необходима правка LK, внести её по подтверждённому контракту.
2. После устранения причины выполнить один контрольный запрос в уже разрешённой
   тестовой КИС. Сохранённый отказ не сбрасывать автоматически.
3. Проверить подтверждённый ID, получателя, состав и количества через gateway,
   затем наличие заказа в истории. Отдельно пройти создание из браузера.

До этого ошибка остаётся открытой. Локальные фикстуры и сборка LK не являются
подтверждением исправления API КИС.
