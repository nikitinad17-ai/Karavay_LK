# Контракт авторизации и каталога доступа — React 3.6

Статус: реализован в ветке `feature/v3.6-user-multi-buyer-auth`; применение схемы к VM выполняется отдельно.

## Модель

```text
users (Auth) → user_buyers (Base) → buyers → outlets
```

- аутентифицируется конкретный пользователь, а не покупатель и не получатель;
- один пользователь может видеть несколько покупателей;
- один покупатель может быть назначен нескольким пользователям;
- `role` в `user_buyers`: `owner`, `manager` или `viewer`;
- в 3.6 эти роли отображаются как контекст доступа; бизнес-операции КИС ещё не подключены;
- `buyers` и `outlets` читаются только как бизнес-справочники.

## Единственный endpoint входа

```http
POST /api/collections/users/auth-with-password
Content-Type: application/json
X-Request-ID: <uuid>

{"identity":"ivan.petrov","password":"<введённый пароль>"}
```

React 3.6 не вызывает `auth-with-password` для `buyers` или `outlets` и не перебирает коллекции после ошибки входа.

Успешный ответ обязан содержать `token` и запись пользователя:

```json
{
  "id": "<PocketBase record id>",
  "login": "ivan.petrov",
  "name": "Иван Петров",
  "active": true,
  "must_change_password": false
}
```

Отсутствие обязательного поля, `active != true` или `must_change_password != false` блокирует вход. Пароль после отправки запроса нигде не сохраняется.

## Загрузка каталога доступа

После успешной авторизации клиент выполняет операции в таком порядке.

1. Загружает только активные связи текущего пользователя:

```http
GET /api/collections/user_buyers/records?filter=user%20%3D%20%22<userId>%22%20%26%26%20active%20%3D%20true
Authorization: <users token>
```

2. Для каждой подтверждённой связи читает соответствующего покупателя:

```http
GET /api/collections/buyers/records/<buyerId>
Authorization: <users token>
```

3. Если активных связей нет, завершает вход ошибкой `NO_BUYER_ACCESS`.
4. При одной связи автоматически выбирает покупателя; при нескольких открывает экран выбора.
5. Только после локальной проверки выбранного `buyerId` по уже загруженному `UserDirectory` получает активных получателей:

```http
GET /api/collections/outlets/records?filter=buyer%20%3D%20%22<buyerId>%22%20%26%26%20active%20%3D%20true
Authorization: <users token>
```

Клиентские `filter` и проверка `buyerId` нужны для корректного интерфейса, но не являются границей безопасности. Те же связи независимо проверяются API rules PocketBase.

## Выбор и смена юрлица

- выбранный покупатель обязан присутствовать в активном `user_buyers` текущего пользователя;
- перед сменой контекста очищаются покупатель, получатель, корзина, заказы, документы, матрица, кэши деталей, последнего заказа и несохранённые корректировки;
- если есть корзина или изменённый, но не сохранённый заказ, сначала требуется явное подтверждение;
- во время загрузки старый buyer-контекст не отображается;
- ответ применяется только если его поколение запроса остаётся актуальным;
- роль выбранной связи хранится в `SelectedBuyerContext`, а не принимается из элемента интерфейса.

## Восстановление после F5

```http
POST /api/collections/users/auth-refresh
Authorization: <users token>
X-Request-ID: <uuid>
```

Алгоритм восстановления:

1. обновить и проверить токен `users`;
2. снова проверить `active` и `must_change_password`;
3. заново загрузить активные `user_buyers` и связанных покупателей;
4. только после этого попытаться восстановить сохранённый `buyerId`;
5. если доступ отозван, не загружать старого покупателя: выбрать единственный оставшийся либо показать экран выбора.

## Хранение на клиенте

В `sessionStorage` сохраняется минимальная сессия:

```json
{
  "token": "<PocketBase token>",
  "collection": "users",
  "userId": "<PocketBase user id>",
  "login": "ivan.petrov"
}
```

Отдельно в `sessionStorage` может храниться только ID последнего выбранного покупателя. Пароль, полная запись пользователя, список связей, покупатели, получатели и КИС-креды не сохраняются. `localStorage` для PocketBase-сессии не используется.

Выход удаляет токен и выбранного покупателя, инвалидирует поколения запросов и очищает всё бизнес-состояние.

## Ошибки клиента

| Код | Значение | Поведение |
|---|---|---|
| `MISSING_CREDENTIALS` | Нет логина или пароля | Оставить форму входа |
| `INVALID_CREDENTIALS` | `users` не принял логин/пароль | Общее сообщение без перечисления коллекций |
| `ACCOUNT_DISABLED` | `active=false` | Запретить вход |
| `PASSWORD_CHANGE_REQUIRED` | `must_change_password=true` | Запретить вход до отдельного сценария смены |
| `INVALID_USER_SCHEMA` | Некорректная запись `users` | Fail-closed |
| `SESSION_EXPIRED` | Refresh отклонён или схема сессии устарела | Полностью очистить сессию |
| `SESSION_USER_MISMATCH` | Refresh вернул другого пользователя | Полностью очистить сессию |
| `NO_BUYER_ACCESS` | Нет активных назначений | Не открывать кабинет |
| `INVALID_BUYER_SELECTION` | Покупатель не входит в каталог пользователя | Не отправлять запрос получателей |
| `DIRECTORY_ACCESS_DENIED` | API rules запретили запись | Не открывать данные |
| `DIRECTORY_SCOPE_VIOLATION` | Сервер вернул чужую связь/точку | Fail-closed |
| `DIRECTORY_INVALID_RECORD` | Поля/relations имеют неверный формат | Fail-closed |
| `DIRECTORY_INVALID_RESPONSE` | Некорректная пагинация/список | Fail-closed |
| `TIMEOUT` / `NETWORK` | PocketBase не ответил | Не использовать mock fallback |
| `BUSINESS_API_NOT_CONNECTED` | Запущен remote-режим без шлюза КИС | Не подменять реальные данные демо-данными |

| Команда | Авторизация | Данные |
|---|---|---|
| `npm run dev` | mock | mock для локальной UI-регрессии |
| `npm run build:demo` | mock | mock |

| `npm run build` | `users` | production remote, fail-closed до подключения КИС |

## Критерии приёмки 3.6

1. Один назначенный покупатель открывается автоматически.
2. Несколько назначений показывают экран выбора.
3. Смена покупателя показывает только его активных получателей.
4. Нет назначений → `NO_BUYER_ACCESS`.
5. Неактивный пользователь и неактивная связь не дают доступ.
6. Чужой buyer/outlet недоступен и на клиенте, и по API rules.
7. F5 сначала повторно проверяет пользователя и связи.
8. Выход полностью очищает сессию и бизнес-контекст.
9. Устаревший ответ переключения не применяется.
10. Несохранённые данные требуют подтверждения перед переключением.
11. Directory-сборка не содержит mock-заказы, цены, документы или КИС-креды.
